Presentations と Product Design の中身を読む

どちらも「plugin」だが、設計思想は違う。Presentations はファイルタイプ特化の制作 runtime、Product Design は複数 skill を束ねたプロダクトデザイン workflow router として動く。

Presentations

PowerPoint / PPTX / Google Slides 向けのデッキ作成、編集、レンダー、検証、エクスポートに特化。

Product Design

アイデア、URL、スクリーンショット、Figma、既存コードから、調査、監査、方向性探索、プロトタイプ作成、共有までをルーティング。

このHTMLはローカルにインストール済みの plugin 本体を一次情報として読んでいる。Product Design は公式 role-specific plugin として導入済み。Presentations は Codex primary runtime に同梱されている。

Presentations は何か

Presentations は、Codex が「スライド」「deck」「PowerPoint」「PPTX」「Google Slides」などの語を見たときに、プレゼン資料作成として扱うためのファイルタイプ wrapper plugin。 中核は Presentations skill 1つで、編集可能な PowerPoint デッキを作ることに強く寄せられている。

主な成果物編集可能な .pptx、レンダー済みプレビュー、レイアウト検証、Google Slides handoff 方針

一言でいうと

「スライドの文章案を書く plugin」ではなく、「資料作成を production workflow として扱い、PPTX をレンダーして検証してから渡す plugin」。

Presentations の実行契約

skill の中身はかなり厳格で、単に pptx を吐けば完了ではない。タスクモードを決め、ストーリーを抽出し、claim spine と design system を固定し、レンダーと QA を通してから最終出力に進む。

1. Modecreate / template-following / targeted-edit を選ぶ。
2. Storyソースから主張と根拠を抽出する。
3. System色、余白、密度、レイアウトリズムを固定する。
4. Buildartifact-tool presentation JSX で編集可能な slide module を作る。
5. QAPNG preview、layout JSON、contact sheet を見て弱いスライドを直す。

重要な制約

  • 通常作成では 1 slide module ごとに presentation.slides.add() する。
  • テンプレ準拠では白紙から似せない。元 PPTX を import して複製 slide を編集する。
  • Python、直接 OOXML 編集、LibreOffice save-as に最終成果物を任せない。
  • 最終納品前に scratch artifacts を消し、最終 .pptx だけを残す契約がある。
Presentations = task mode + claim spine + design system + editable build + render QA + PPTX export

Presentations を使うとき

向いている

  • 投資家向け、業績、戦略、プロダクト説明、技術説明の deck
  • 既存テンプレに沿った PPTX の編集
  • レンダー確認込みで見た目を整えたい資料
  • 最終ファイルとして PowerPoint が必要な作業

向いていない

  • 単にスライド構成だけ欲しい軽い相談
  • データの出典がなく、見栄え優先で数字を埋めたい依頼
  • Google Slides へ直接保存したいが connector がないケース
  • テンプレを無視して自由に作りたいが、元デッキ準拠を求める依頼

Product Design は何か

Product Design は、早期アイデア、ライブURL、静的スクリーンショット、既存プロトタイプ、保存済みのデザイン文脈を、チームがレビューできるプロトタイプや監査結果に変える plugin。 1つの巨大 skill ではなく、目的別 skill をルーターが振り分ける構造になっている。

apps.app.json に sites binding。現インストールでは ID が placeholder のまま。
主な成果物UX research、flow audit、3方向の visual ideation、URL clone、image-to-code prototype、share URL

現在のローカル copy では .app.json の sites.id が REPLACE_WITH_SITES_APP_OR_CONNECTOR_ID のまま。つまり prototype 制作自体は読めるが、Sites 共有は追加セットアップなしでは完了しない可能性が高い。

Product Design のルーター構造

入口は index skill。ユーザーが @Product Design と呼ぶか、設計、監査、調査、プロトタイプ、URL clone、image-to-code、share などを頼むと、この router が適切な focused skill に流す。

Context系

user-context と get-context が、保存済み参照と今回のbriefを確定する。

Explore系

research、audit、ideate が、調査、監査、3方向の視覚案を担当する。

Build / Share系

prototype、url-to-code、image-to-code、design-qa、share が実装と共有を担当する。

Product Design の skill 一覧

skill役割止める条件
index全体ルーティング。 broad request を focused skill に振り分ける。自分では成果物を作らない。
user-context保存済み product/design context の読み書き。保存済み情報を無関係に全部読まない。
get-contextbrief gate。何を、何に合わせ、どこまで動かすかを確認。文脈が足りない間は実装しない。
ideateImage Gen で visual direction を作る。brief 未確認では生成しない。
prototypeプロトタイプ作成 workflow の選択。visual target なしでは build しない。
url-to-codeURL を frontend-only local app として再現。権限・利用規約・source capture が確認できない場合は止まる。
image-to-code選択済み画像や mockup を responsive frontend にする。選択済み visual target がないと開始しない。
design-qasource visual と実装 screenshot を比較し、差分修正を出す。source と implementation を同じ状態で比較できないと blocked。
auditproduct flow を screenshot evidence 付きで監査。スクショだけで確認不能な限界を明示する。
researchUX friction を公開ソースなどから調査。観測 evidence と inference を混ぜない。
share選択済み deployment target で prototype を共有。target 未選択、または tool 不在なら共有完了と主張しない。

Product Design の重要なガードレール

この plugin の肝は、デザイナーっぽく自由に作ることではなく、作り始める前に evidence と visual target を固定すること。

No visual target, no build

brief は visual target ではない。URL、スクリーンショット、Figma frame、選択済み Image Gen 案などが必要。

Get context first

設計、build、clone、redesign、prototype では get-context を先に通す。

Evidence-backed QA

source image と実装 screenshot を同じ比較入力に置いて、見える差分から直す。

Real assets

見える asset を ASCII、placeholder、手描きSVG、CSS art でごまかさない。必要なら Image Gen を使う。
