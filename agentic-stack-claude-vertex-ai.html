動画の主張

動画の主張は、「Agent開発の勝負どころは、モデル呼び出しのコードではなく、その周辺の標準化と運用にある」というものです。 LLMを呼ぶだけなら、どのフレームワークでも短いコードでできます。しかし実際のアプリケーションでは、以下がすぐ問題になります。

  • Agentごとにツール接続の実装が違い、再利用しづらい。
  • LangGraph、CrewAI、ADKなど、異なるフレームワークで作ったAgent同士が自然に協調できない。
  • ローカルデモから本番へ移すと、API化、コンテナ化、スケール、ログ、監視、評価、権限管理が一気に必要になる。
  • 複数Agentを増やすほど、どのAgentが何をしたのか、なぜそのツールを呼んだのかを追跡する必要が出る。
重要:

X投稿では「AnthropicがデモAgent時代を終わらせた」という表現になっていますが、動画そのものは Anthropic単体のAgent SDK紹介ではなく、Google CloudがVertex AI上で示すAgentic Stackの実演です。

4層のAgentic Stack

動画では、Agentを本番運用へ近づけるために4つの層を組み合わせます。 それぞれの役割は重なっているようで、実際には責任範囲が違います。

ADK
Agentをコードとして定義する層。 `LLMAgent`、モデル、指示、ツール、Runner、Sessionなどを使って、Agentの振る舞いをアプリケーション構造に落とす。
MCP
ツールとコンテキスト接続を標準化する層。 既存のMCPサーバーをADKのToolとして取り込み、Agentが外部サービスを使えるようにする。
Agent Engine
Agentを本番サービスとして動かす層。 デプロイ、スケール、ログ、監視、セッション、評価連携など、アプリ運用の面倒を見る。
A2A
Agent同士の共通言語を作る層。 異なるフレームワークや基盤で動くAgentが、自分の能力を公開し、互いに依頼を出せるようにする。

ADKの中核概念

概念 動画での説明 実務的な意味
LLMAgent LLMを「脳」とする最もシンプルなAgentパターン。 モデル名、説明、指示、ツールを明示して、Agentの責務をコード上で固定する。
Tool Agentに与える能力やアクション。Python関数やMCPツールを使える。 LLMが外部世界に作用する境界。権限、入力スキーマ、失敗時の扱いが重要になる。
Runner Agentを実行し、会話やツール呼び出しをまとめる実行器。 Agent本体とユーザーインターフェースの間にある実行制御の層。
Session 会話状態を保持する単位。以前の会話を覚えた形でやり取りできる。 ステートレスなLLM呼び出しを、ユーザー体験として連続したものに変える。
adk run AgentをCLIで対話的に動かす。 最小実装の動作確認とプロンプト・ツール挙動の反復に向く。
adk web Web UIでAgentの実行を観察する。 多Agent構成で、どのAgentがどの処理を担当したかを確認しやすい。

ClaudeをVertex AIで使う流れ

動画では、まずVertex AI Model Gardenを開き、AnthropicのClaudeモデルを選びます。 Model Gardenは、Googleのモデルだけでなく、パートナーモデルやオープンモデルを見つけて使うための入口として説明されています。

デモでは Claude 3.7 Sonnet を使ってAgentを作ります。 イベント当日の文脈ではClaude 4にも触れていますが、ADKとの統合は「今後対応」といった位置づけで説明されています。 ここで重要なのは、モデルを直接Anthropic APIだけで呼ぶ話ではなく、Vertex AIの認証、コンソール、API導線に乗せる点です。

Lab 1: 誕生日プランナーAgent

最初の実装は、誕生日会の企画を助けるシンプルなAgentです。 役割は、テーマ案、ゲストリスト、準備の相談などに答えることです。 動画では、Agentを動かすための最小構成として、概ね次のようなファイル構成が示されます。 

birthday_planner_agent/
  __init__.py
  agent.py
  .env

`agent.py` では、ADKのAgentクラスとClaudeモデルをimportし、名前、モデル、説明、指示を渡してAgentを作ります。 ここでのポイントは、Agentが「何でも屋」ではなく、説明と指示で責務を絞られていることです。 

# 概念的な形。動画の画面コードを厳密転写したものではありません。
birthday_agent = LlmAgent(
    name="birthday_planner_agent",
    model=Claude(...),
    description="Helps plan birthday parties",
    instruction="Suggest themes, plans, and useful next steps.",
    tools=[],
)

これを adk run birthday のように起動すると、CLI上でAgentと対話できます。 この段階では、Agentは主にLLMの知識と指示で答えるだけで、外部カレンダーなどにはまだ接続していません。

Lab 2: MCPでカレンダー連携を足す

次の段階では、「誕生日の案を出す」だけでなく、「プレゼントを買いに行く予定をカレンダーに入れる」 といった外部アクションが必要になります。ここでMCPが登場します。

動画では、既存または自作のMCPサーバーへ接続し、そのMCPサーバーをADKのToolとして扱う流れが説明されます。 MCPサーバー側が提供する能力をADKが読み取り、Agentが呼べるツールへ変換する、という理解でよいです。

User 誕生日相談や予定登録を依頼する。
Orchestrator 依頼の種類を見て担当Agentを選ぶ。
Birthday Agent テーマ、準備、ギフト案を考える。
Calendar Agent MCP経由で予定を扱う。
MCP Server カレンダー操作など外部機能を提供する。

この時点で構成は単一Agentから多Agentシステムになります。 誕生日プランナーはそのまま残し、カレンダーAgentを追加し、さらにオーケストレーターAgentが両者をToolのように扱います。 動画では、誕生日案の生成にはGeminiを使い、カレンダー側にはClaudeを使うようなハイブリッド構成にも触れています。

オーケストレーターの意味

オーケストレーターは、単に「複数の関数を順番に呼ぶ」ものではありません。 ユーザーの依頼を読んで、どのAgentに任せるべきかを判断するAgentです。 そのため、オーケストレーター自身にも明確なinstructionが必要になります。

単一Agentの場合

ユーザーの全依頼を1つのAgentが受ける。実装は簡単だが、ツールや責務が膨らむと管理しづらい。

多Agentの場合

専門Agentを分け、オーケストレーターが依頼を振り分ける。責務は明確になるが、観測性とルーティング設計が必要になる。

ADKのWeb UIは、この多Agent構成のデバッグに役立つものとして紹介されています。 会話の裏側で、どのAgentが呼ばれ、どのツールが使われたのかを確認できるためです。

Lab 3: Agent Engineで本番化する

動画の後半で最も重要なのがAgent Engineです。 ローカルでAgentを作っただけでは、社内外のユーザーが安定して呼べるサービスにはなりません。 通常なら、AgentをAPIに包み、Webフレームワークを選び、コンテナを作り、クラウド環境へ出し、ログと監視を整える必要があります。

登壇者は、この手作業の例としてFastAPIやDjango、コンテナ、GCP実行環境、インフラ運用、モニタリングを挙げます。 Agent Engineは、その運用面をマネージドにするための層として紹介されます。

自前で必要になりがちなもの Agent Engineが担う範囲
AgentをHTTP APIとして包む Agentをデプロイ可能なリソースとして扱う
コンテナ作成、依存関係、実行環境 requirementsやAgent定義からデプロイを進める
スケール、CPU、メモリ、レイテンシ監視 Vertex AIの管理UIで確認できる
会話ログとセッション管理 セッションやリクエスト情報を管理対象にする
Agent改善のための評価データ ログを評価サービスへつなげ、継続改善の材料にする

デプロイコードの形

動画では、最後のLabとして、リポジトリ内のデプロイ用モジュールを実行します。 概念的には、Agent本体とrequirementsを渡し、Agent Engine上にエンドポイントを作る流れです。 

# 概念的な形。動画の画面コードを厳密転写したものではありません。
remote_agent = AgentEngine.create(
    agent=local_birthday_agent,
    requirements=[
        "google-cloud-aiplatform",
        "google-adk",
        "anthropic-or-vertex-related-package",
    ],
)

デプロイが走ると、裏側でイメージのビルドやリソース作成が行われます。 完了後はVertex AI Agent EngineのUIで、デプロイ済みAgent、セッション、詳細情報、呼び出し方法、 そしてクエリ数やレイテンシ、CPU/メモリなどを確認できます。

A2A Protocolの位置づけ

A2Aは、動画では最後のボーナス的な紹介です。 ただし、考え方としてはかなり重要です。Agent EngineはADK以外のフレームワークも受け入れられるが、 異なるフレームワークで作られたAgent同士が自然に会話するには、共通のプロトコルが必要になります。

Agent Skill Agentができる具体的な機能や能力。A2A文脈での「Skill」は、CodexのSkillとは別物。
Agent Card Agentのデジタル名刺。どんな能力があり、どう呼び出せるかを他Agentやアプリへ伝える。
Agent Executor Agent間のリクエストとレスポンスを実際に処理する実行部分。
Protocol Base HTTPやJSON-RPCのような一般的な標準の上に組むため、企業環境で扱いやすいという説明。

Codex/Claude Code Skillとの違い

ここがユーザー視点で一番混同しやすいところです。 CodexやClaude CodeでSkillをゴリゴリにカスタマイズすると、かなり高度な作業者AIになります。 しかし動画で扱っているAgentとは、主な責務が違います。

観点 Codex / Claude Code Skill 動画のAgent
本質 既存の作業者AIへ手順、判断基準、補助スクリプトを足す。 特定目的のAIアプリケーションを独立した単位として作る。
実行主体 人間がCodexやClaude Codeへ依頼し、そのセッション内で動く。 API、UI、他Agent、社内システムから呼ばれる。
リモート性 ローカル中心だが、外部APIを叩くSkillも作れる。 ローカルでも動くが、本番ではリモートの常時稼働サービスになりやすい。
状態 会話、ワークスペース、CLI実行履歴に依存しやすい。 Session、Memory、DB、ログなどを設計対象にできる。
運用責任 基本は人間の作業支援なので、失敗時は人間が拾う。 サービスとして、監視、スケール、失敗時挙動、権限、評価が必要。
他Agent連携 主に同じ作業環境内のツール連携。 A2AやAgent Cardで、外部のAgentと発見・依頼・応答する方向。
remoteにあるかどうかだけではない

remoteに置くことは違いの一部ですが、核心ではありません。 Skillは「作業者AIの振る舞いを濃くするもの」、Agentは「外部から仕事を受けられるソフトウェア単位」です。

本番化で見るべきリスク

動画は製品紹介のトーンなので、実務では追加で見ておくべき点があります。 Agent Engineが運用面を軽くしても、設計責任が消えるわけではありません。

  • 権限境界: カレンダー、メール、DB、決済などをTool化する場合、Agentにどこまで許すかを明確にする。
  • プロンプト注入: MCP経由で取得した外部データが、Agentの指示を書き換える形にならないようにする。
  • 観測性: 失敗した応答だけでなく、どのToolをなぜ呼んだかを追える必要がある。
  • 評価: 「答えが自然」ではなく、ツール選択、手順、権限遵守、最終結果を評価する。
  • コスト: 多Agent構成では、1つのユーザー依頼で複数モデル呼び出しが連鎖しやすい。
  • 責務分割: Agentを分けすぎるとルーティングが複雑になり、分けなさすぎるとTool肥大化が起きる。

実務での使い分け

この動画の内容を、CodexやClaude Codeで日々作業している開発者向けに言い換えると、次の判断になります。

Skillでよいケース

  • 人間が監督する開発作業を速くしたい。
  • リポジトリ固有の手順、レビューポリシー、生成形式を覚えさせたい。
  • 失敗時にその場で人間が修正できる。
  • 常時稼働APIや複数ユーザー向け運用は不要。

Agent化するケース

  • 社内システムやユーザーから継続的に呼びたい。
  • セッション、権限、監視、ログ、評価を運用対象にしたい。
  • 他Agentや外部ツールと標準プロトコルでつなぎたい。
  • 人間が毎回Codex/Claude Codeを開かなくても仕事が進む必要がある。

したがって、最初はSkillでワークフローを固め、再現性が出てきたらAgentとしてAPI化・常時稼働化する、 という移行はかなり自然です。

持ち帰るべきポイント

  1. この動画の主役は「Claudeを呼ぶ方法」ではなく、Agentを本番運用へ運ぶための周辺構造。
  2. ADKはAgentをコードとして定義するための層で、Skillのような手順書とは責務が違う。
  3. MCPは外部ツール接続の標準化。Toolが増えるほど価値が出る。
  4. Agent Engineはremote実行だけでなく、ログ、監視、セッション、評価導線を含む運用基盤。
  5. A2Aは、Agentが増えた世界で「発見して依頼する」ためのプロトコル。
  6. Codex/Claude Code Skillは強力な作業環境拡張。Agentは独立して仕事を受けるソフトウェア単位。
