GBrain の設計メンタルモデル

前の解説は実装の地図に寄りすぎていました。ここではコードの細部ではなく、 GBrain がどういう発想で設計されているかを説明します。

核心はこれです。GBrain は「AI に長期記憶を持たせるシステム」ではなく、 人間の世界についての知識を、証拠つきのページ、検索インデックス、関係グラフ、 判断手順、バックグラウンド処理に分解して、エージェントが毎回そこへ戻ってくるようにする設計です。

1. まず 1 文で捉える

GBrain のメンタルモデルは、こうです。 

AI agent の「その場の会話能力」に、
人間が読める dossier 群と、
機械が検索できる index/graph と、
繰り返し運用できる skill/job を接続する。

ここで大事なのは、GBrain は「全部をベクトル DB に投げる」設計ではないことです。 情報の種類ごとに置き場所と更新ルールを変えています。

種類置き場所なぜ分けるか
現在の会話 session context 今だけ必要。永続化しない。
エージェントの操作方針 agent memory 「短く答えて」「本番前に staging」など、世界の知識ではなく振る舞いの設定。
人・会社・会議・概念・自分の考え GBrain 世界についての永続知識。後で検索・引用・更新する。

この分類は docs/guides/brain-vs-memory.md の中心です。 「Pedro は Brex の CEO」は GBrain、「回答は箇条書きが好き」は agent memory、「今この PR を見ている」は session。 これを混ぜると、個人 dossier が消えたり、運用 preference が知識ページを汚したりします。

2. 解こうとしている問題

GBrain が前提にしている問題は、普通の AI agent が「賢いが忘れる」ことです。 ただし「忘れる」といっても、単にログを保存すればよいわけではありません。

単なるログ保存が弱い理由

  • 会議 transcript が 200 件あるだけでは、今の結論がわからない。
  • ベクトル検索だけでは「誰が誰に投資したか」「誰が会議に出たか」の関係質問に弱い。
  • エージェントの会話履歴だけでは、人間が読んで修正できる正本にならない。
  • LLM に全部やらせると、同じ入力でも結果がぶれるし、定期処理が高コストになる。

GBrain の答え

GBrain は「保存」ではなく「構造化された知識運用」を作ろうとしています。 

生の出来事
  -> どの entity の話か検出する
  -> その entity の dossier に追記する
  -> 現在の理解を rewrite する
  -> 証拠ログは append-only で残す
  -> relation は graph edge にする
  -> 検索 index を更新する
  -> 次の会話では brain first で読む

3. 設計の第一原理: 記憶を 3 層に分ける

GBrain の最初の設計判断は、「何でも長期記憶に入れる」ではありません。 記憶を session、agent memory、brain に分けます。

Session

現在の作業状態。今の依頼、直前の会話、開いているファイル。自然に context window にある。

Agent Memory

エージェントの操作方法。ユーザーの好み、デプロイ手順、ツール設定、会話継続のための作法。

GBrain

世界の知識。人、会社、会議、概念、アイデア、関係、証拠、評価。

ここでの設計感覚は、OS の memory 階層に近いです。 レジスタ、RAM、ディスクを同じ扱いにしないように、会話 context、操作記憶、世界 knowledge も同じ扱いにしません。

重要な罠: 「Pedro prefers email」は preference に見えますが、Pedro という人についての事実なので GBrain。 「ユーザーは短い回答を好む」は agent の操作方針なので agent memory。 この区別が GBrain の設計の入口です。

4. 設計の第二原理: ページはログではなく dossier

GBrain のページは、Obsidian 的なメモでも、単なる transcript の束でもありません。 目指しているのは「その entity について 30 秒で現状がわかり、必要なら証拠に戻れる dossier」です。

Compiled Truth + Timeline

ページは 2 つの領域に分かれます。

領域更新ルール意味
Compiled truth rewrite 現在のベストな理解。古い評価は新しい情報に合わせて書き換える。
Timeline append-only 証拠の履歴。既存 entry は編集せず、新しい証拠や訂正を追加する。

これがかなり重要です。append-only ログだけだと、半年後に読むときに 200 件の履歴から自分で要約する必要があります。 compiled truth があると、今の評価、相手の状況、関係性、次に注意すべきことがすぐ読めます。 timeline はその評価を支える証拠です。 

Person page
  compiled truth:
    - 何者か
    - 今の状態
    - 何を信じているか
    - 何を作っているか
    - 自分の assessment
    - trajectory

  timeline:
    - 2026-04-07: 会議でこう話した
    - 2026-04-03: メールでこう言っていた
    - 2026-03-15: 初回 meeting

つまり GBrain のページは「検索結果の保存先」ではなく、「継続的に更新される intelligence profile」です。

5. 設計の第三原理: Brain-Agent Loop

GBrain は静的なデータベースではなく、エージェントとのループで価値を出します。 docs/guides/brain-agent-loop.md はこれをそのまま説明しています。 

Signal arrives
  -> DETECT: 人・会社・概念・アイデアを拾う
  -> READ: 返答前に brain を読む
  -> RESPOND: brain context を使って答える
  -> WRITE: 新情報を brain page に反映する
  -> SYNC: index を更新する
  -> 次回の READ が強くなる

ここでの設計思想

普通の agent は「質問に答える」で終わります。 GBrain は「質問に答えるたびに、次の質問に強くなる」ことを狙っています。 つまり、会話は単発の入出力ではなく、brain を改善する event です。

このループが回ると、半年後には agent が「外部 API で調べた一般情報」ではなく、 「自分がその人と何を話したか」「自分はその会社をどう評価していたか」「最近何が変わったか」を前提に答えられます。

6. 設計の第四原理: Latent と Deterministic を分ける

GBrain の思想文書で最も設計らしいのは Thin Harness, Fat Skills です。 ここでの中心は「LLM にやらせるべき仕事」と「決定的コードに落とすべき仕事」を分けることです。

分類得意なことGBrain での置き場所
Latent / Judgment 読む、評価する、矛盾を見つける、何が重要か判断する、dossier にまとめる。 Skills、agent workflow、compiled truth rewrite。
Deterministic 同じ入力なら同じ出力。SQL、chunking、embedding、graph traversal、job retry、auth。 CLI、DB、operations、Minions。

これは GBrain の設計全体に通っています。 例えば「この meeting transcript から何が重要か」は判断なので skill。 「既存ページを検索する」「edge を insert する」「job を retry する」は決定的処理なのでコード。

雑にいうと、GBrain は LLM を「何でも実行する worker」として使うのではなく、 「判断が必要なところだけに置く」設計です。信頼性が必要な部分は Postgres、CLI、schema、job queue に寄せます。

7. なぜベクトル検索だけではないのか

GBrain は hybrid search を持ちますが、設計上もっと重要なのは「text を relation に変換する」ことです。 これは knowledge graph の発想です。

ベクトル検索が得意な質問

  • このテーマに近いメモはどれか。
  • この言い換えに意味的に近い文章はどれか。
  • 自分が過去に似た考えを書いていないか。

グラフが得意な質問

  • 誰が Acme に勤めているか。
  • Bob が投資した会社はどれか。
  • Alice と Carol はどの会議や会社でつながっているか。
  • この founder の trajectory は時間とともに改善しているか。

vector は「似ている」を扱う。graph は「関係している」を扱う。 GBrain はこの 2 つを混ぜています。だから「検索エンジン」というより「個人世界モデル」に近い。 

Text:
  "Alice is CEO of Acme and Bob invested in Acme."

Derived graph:
  people/alice --works_at/founded?--> companies/acme
  people/bob   --invested_in-------> companies/acme

8. Skills は「プロンプト」ではなく「判断手順のソースコード」

GBrain の skills は、単なるプロンプト集ではありません。 設計上は「agent が何をどう判断するか」を Markdown で配布する仕組みです。 docs/ethos/MARKDOWN_SKILLS_AS_RECIPES.md では、Markdown を software distribution の単位として扱っています。

なぜ Markdown なのか

  • LLM が直接読める。
  • 人間もレビューできる。
  • 判断基準、失敗時の処理、例外、哲学を書ける。
  • コードより柔らかく、ただの自然文より構造化できる。

Skill の設計上の役割

役割説明
Procedure meeting ingestion、email triage、enrichment などの手順を定義する。
Judgment carrier 何を重要とみなすか、どう評価するか、どこまで調べるかを記述する。
Resolver target タスクに応じて、agent がどの skill を読むべきか決める。
Distribution unit 別の agent 環境にも recipe として配れる。

ここが GBrain の発想としてかなり独特です。 「LLM を賢くする」のではなく、「LLM が読むべき手順・判断基準・失敗モードを Markdown として蓄積する」。 その結果、モデルが変わっても skills は残り、同じ手順がよりよく実行される、という設計です。

9. Minions は「LLM にやらせない」ための設計

Minions は、GBrain の中でかなり重要な設計判断です。 これは「エージェントをもっと増やす」機能ではなく、逆に「LLM が不要な仕事を LLM から取り上げる」機能です。

仕事載せる場所理由
tweet を取得して JSON を parse して brain page に書く Minion job 手順が決まっている。token を使う必要がない。
会議 transcript から重要な人物・評価・関係を判断する Skill + LLM 何が重要か判断が必要。
毎朝 sync / extract / doctor を走らせる Minion job / cron 繰り返し可能な運用処理。
メールに返信すべきか判断する LLM / skill 文脈と優先度の判断が必要。

つまり Minions は「耐久性」「再試行」「親子ジョブ」「進捗」「停止/再開」を DB に持たせることで、 LLM ループの不安定さを運用処理から切り離す設計です。

10. 境界設計: Brain / Source / System of Record

Markdown repo が正本、DB は派生 cache

docs/architecture/system-of-record.md の中心は、 「GitHub repo の Markdown + frontmatter が system of record。Postgres/PGLite は derived cache」という契約です。

この設計により、DB が壊れても Markdown repo から rebuild できます。 人間は Markdown を読んで編集できます。 DB は検索、dedup、embedding、graph materialization のために使います。 

Markdown repo = canonical knowledge
DB = derived index / graph / runtime state

user knowledge:
  markdown first

runtime infra:
  db-only allowed
  examples: oauth tokens, job queue, request logs

Brain と Source

docs/architecture/brains-and-sources.md は、知識のスコープを 2 軸で分けます。

概念意味境界
Brain どの DB か。 所有者・アクセス権・ライフサイクルの境界。
Source その DB 内のどの repo / corpus か。 同じ所有者内の namespace 境界。

例えば「個人 brain」と「media team brain」は別 Brain。 個人 brain の中の「wiki」「gstack」「essays」は別 Source。 これは設計上、権限・引用・検索対象の混線を防ぐためです。

11. GBrain を設計図として見るなら、登場する基本オブジェクトはこれ

プリミティブ設計上の意味
Page 人・会社・概念などの dossier。current synthesis と evidence trail を持つ。
Timeline Entry いつ何が起きたかの証拠。append-only。
Fact / Take 構造化された主張。後で検証、矛盾検出、trajectory に使う。
Link / Edge entity 間の関係。検索ではなく関係質問のための構造。
Chunk 検索単位。ページ本文から作られる派生 index。
Skill LLM に読ませる判断手順。Markdown で書かれた capability。
Operation CLI/MCP から呼ぶ安定 API。権限と trust boundary を持つ。
Minion Job LLM ではなく DB queue で動かす決定的バックグラウンド処理。
Brain DB 境界。所有者と権限の単位。
Source Brain 内の repo/corpus 境界。

12. なぜこの設計は「個人知識」に向いているのか

個人知識は、公開 web knowledge と違って次の性質があります。

  • 関係性が重要。誰をどう知っているかが価値。
  • 評価が重要。LinkedIn にない自分の assessment が価値。
  • 時間変化が重要。昔の評価と今の評価が違う。
  • 証拠が重要。なぜそう思っているかを追える必要がある。
  • 漏洩リスクが高い。remote/tool/API 境界を慎重に扱う必要がある。

GBrain の compiled truth、timeline、links、facts、source scope、remote stripping は、全部この性質に対応しています。 だから普通の RAG より複雑です。複雑なのは、扱っている情報が「ドキュメント検索」ではなく「自分の世界モデル」だからです。

13. まとめ: GBrain の設計を 7 つの原則で覚える

  1. Brain は世界知識、memory は操作方針、session は現在作業。 まず置き場所を間違えない。
  2. ページは dossier。 現在の理解は rewrite、証拠は append-only。
  3. 毎回 brain first。 外部 API は fallback。自分の文脈が先。
  4. 検索だけでなく関係も保存する。 vector は similarity、graph は relation。
  5. 判断は skill、実行は deterministic tooling。 LLM に全部やらせない。
  6. Markdown が正本、DB は派生 index。 人間可読性と再構築性を維持する。
  7. 運用処理は Minions。 繰り返し処理・再試行・cron を LLM loop から外す。

一番短くいうなら、GBrain は「AI agent 用の個人 CRM + research notebook + knowledge graph + workflow runtime」です。 ただし、正本は Markdown、検索は DB、判断は skills、反復処理は jobs、という分業で作られています。
