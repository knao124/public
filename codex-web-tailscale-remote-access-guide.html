codex-web を外のネットワークから使うときの考え方

結論だけ先に言うと、codex-web はそのままインターネットに公開する前提の作りではありません。 外出先から安全寄りに使いたいなら、VPN、Tailscale、WireGuard、SSH トンネルのような 「外側の安全な通路」を作る前提で考えるのが正しいです。

Overview

このプロジェクトは「ブラウザ UI」と「その裏で動く codex の実行環境」を同じマシン上に寄せる設計です。 ブラウザで見えているのはフロントエンドですが、実際にはその UI 経由でホストマシン上の codex を動かせます。

つまり、外からアクセスできる人は、ほぼ「そのホスト上で codex を触れる人」と考えるべきです。

全体アーキテクチャ図

外部端末から見たときの全体像は次の通りです。重要なのは、保護レイヤの内側に入った時点で Web UI だけでなく、その背後の codex 実行環境にも届くことです。

実際のリスク

README の説明どおり、Web UI に届く人は次のことができる前提で考えるべきです。

  • ホスト上でコマンドを実行する
  • 読める権限のあるファイル、環境変数、SSH キー等へ触れる
  • そのマシンでサインイン済みの codex / ChatGPT アカウントを使う

なので「公開 URL を作って、Basic 認証だけ付ければ十分」とまでは言いづらいです。 まずはネットワーク自体を閉じる方が筋が良いです。

どう使うのが現実的か

個人用途なら次の順で考えるのがわかりやすいです。

  • 一番無難: ホストでは 127.0.0.1 のまま動かし、Tailscale / WireGuard / SSH トンネル経由でだけ入る
  • LAN 内だけ: --host 0.0.0.0 にして、家庭内や社内の信頼できるネットワークからだけ使う
  • 公開運用に近い形: 逆プロキシで TLS を終端しつつ、さらに VPN や認証ゲートを前段に置く

モバイルから使いたいなら、Tailscale のように端末同士を閉域でつなぐやり方がかなり相性が良いです。

Tailscale を理解するための基本用語

ここは codex-web を Tailscale 越しに使うために必要な用語を、 上から順に読めばつながるように並べた節です。Tailscale 全機能の完全な辞書ではなく、 この用途で混乱しやすい言葉を一通りまとめています。

1. Device / Client: まず何が参加するのか

Tailscale の client は、PC、スマホ、サーバーのような device に入れるソフトです。公式の用語集でも、client は 「端末が tailnet に参加して活動するためのアプリ」とされています。

つまり、人が直接 tailnet に入るというより、まずは「端末に Tailscale client を入れる」が出発点です。

2. User / Sign in / 参加: 誰の端末として入るのか

端末に client を入れただけでは不十分で、次にその端末をどのアカウントで Tailscale にログインさせるかを決めます。これでその端末は特定の tailnet に属するようになります。

Tailscale の用語では node は「user と device の組み合わせ」です。 なので「この Mac を自分の tailnet に参加させる」というのは、 厳密には「自分のユーザーとして、その Mac を node 化する」に近い理解です。

3. Tailnet: 参加先の私的な空間

tailnet は Tailscale のネットワークそのものです。 公式には「users, devices, resources の相互接続された集合」と説明されています。

ここで言う「空間」はこの tailnet のことです。 同じ tailnet に入っている端末同士は、Tailscale のルールに従って互いを見つけて通信できます。

4. Peer: その空間の中で相手になる端末

自分の端末が通信しようとしている別の node を peer と呼びます。 たとえば iPhone から自宅サーバー上の codex-web に入るなら、 そのサーバーは iPhone から見た peer です。

5. Tailscale IP: tailnet の中での固定っぽい住所

各端末には 100.x.y.z 形式の Tailscale IP が付きます。 これは自宅 Wi-Fi、テザリング、カフェの回線などに変わっても維持されやすい、 tailnet 内での安定したアドレスです。

「家の回線のグローバル IP が変わるから困る」という問題を、 ある程度この安定した内部アドレスで隠してくれる、と思うと理解しやすいです。

6. MagicDNS / ts.net: IP ではなく名前で呼ぶ仕組み

MagicDNS は、tailnet 内の端末へ自動で DNS 名を付ける機能です。 これが有効だと、数字の IP ではなく名前で相手に届きやすくなります。

特に共有マシンでは <hostname>.<tailnet-name>.ts.net のような 完全修飾名が出てきます。Tailscale を使っていると URL や接続先に .ts.net が出てくるのはこのためです。

7. Overlay network / Tunnel / WireGuard: どうやってつながるのか

Tailscale は public internet の上に重ねる overlay network です。 下にある通常の Wi-Fi やモバイル回線が underlay、その上に暗号化された tunnel を作るのが Tailscale です。

公式用語集では client は WireGuard を使って暗号化された peer-to-peer 接続を作ると説明されています。 ここで大事なのは「普段のインターネットを捨てる」のではなく、 その上に私的な通信路を追加する、という感覚です。

8. NAT traversal / DERP: 直接つながらない時にどうするか

現実のネットワークには NAT やファイアウォールがあるので、端末同士が常に直接つながるわけではありません。 そのため Tailscale は NAT traversal を使って、まずは直接接続を試みます。

それでも無理なときは、公式用語集にある DERP relay という中継を使います。 なので「Tailscale は常に中央サーバーを経由する VPN」という理解は少しズレています。

9. 同じ tailnet に参加することと、共有してもらうことは別

ここがかなり重要です。同じ tailnet に参加するとは、あなたの端末がその tailnet の内部メンバーになることです。 一方で sharing は、別 tailnet のマシンを限定的に見せてもらう仕組みです。

公式の共有ドキュメントでは、共有マシンはデフォルトで quarantine され、 受け手側へ見せる情報も最小限です。個人で自分の PC とスマホをつなぐなら、 まず考えるのは sharing より「同じ tailnet に両方参加させる」です。

10. Access control / Grants / ACLs: 空間の中で誰が何に触れるか

同じ tailnet にいるだけで無制限に何でもしてよい、とは限りません。 Tailscale では tailnet policy file でアクセス制御を管理します。

新しい書き方は grants、古い書き方は ACLs です。 どちらも「誰が」「どの端末やサービスへ」「どのポートや機能で」届けるかを決めるためのものです。 codex-web を人に見せるなら、この層の理解も重要です。

11. Serve と Funnel: 端末の中のローカルサービスをどこまで見せるか

Serve は、端末上のローカルポートを tailnet 内だけに見せる機能です。 公式ドキュメントでも、Serve は tailnet 内向け、Funnel は public internet にも出す機能として区別されています。

codex-web を使う文脈では、127.0.0.1:8214 で動くローカルサービスを 自分の端末群にだけ見せたいので、基本的には Serve を使います。

12. Exit node と subnet router: よく似て見えるが別物

exit node は、一般のインターネット向け通信を特定の端末経由にする仕組みです。 典型的な VPN の「全部そこから出す」に近い機能です。

subnet router は、Tailscale client を入れていない社内 LAN や VPC の奥へ入るためのゲートウェイです。 codex-web を自分の端末から触るだけなら、まず必要なのはこの2つではなく 「同じ tailnet に参加」+「Serve」です。

参考: Terminology and concepts, DNS in Tailscale, Sharing, Access control, Grants, Exit nodes, Subnet routers, Tailscale Serve

iPhone を tailnet に参加させて、5G から自宅 Mac に入るには

ここでは「自宅の Mac で codex-web を動かし、それを外出先の iPhone から 5G 回線で開く」という具体例で説明します。結論だけ先に言うと、 自宅ルーターでポート開放をしなくても、Mac と iPhone を同じ tailnet に参加させ、 Mac 側で tailscale serve を設定すれば足ります。

通信のイメージ

iPhone 5G 回線上で Tailscale の VPN を有効化
→
Tailscale tailnet NAT 越えを自動処理し、必要なら DERP relay を使う
→
自宅 Mac codex-web は localhost、tailscale serve で tailnet にだけ公開

必要な準備は次の 4 つです。

  • 自宅 Mac に Tailscale を入れて、あなたの tailnet にログインしておく
  • iPhone に Tailscale アプリを入れて、同じ tailnet にログインする
  • Mac 側で codex-web を起動しておく
  • Mac 側で tailscale serve を設定して、localhost の 8214 番を tailnet 内 HTTPS として見せる

手順 1. 自宅 Mac を tailnet に参加させる

自宅 Mac へ Tailscale client を入れ、あなたのアカウントでサインインします。 Tailscale の公式ドキュメントでは、新しい端末で認証するとその端末は tailnet に追加されます。 もし device approval を有効にしているなら、管理画面の Machines で承認が必要です。

手順 2. iPhone を同じ tailnet に参加させる

iPhone でも Tailscale アプリを入れて、同じアカウントまたは同じ tailnet に入れるアカウントでログインします。 初回は iOS の VPN 構成追加の許可が出るので、それを許可します。 これで iPhone も tailnet の node になります。

Tailscale の iOS ドキュメントでは、必要なら VPN On Demand を設定できます。 5G で毎回自動接続したいなら、Cellular を Always にすると、 iPhone がモバイル回線に乗った時に自動で Tailscale を張りやすくなります。

手順 3. Mac で codex-web を localhost のまま起動する

codex-web はデフォルトで 127.0.0.1:8214 にだけ待ち受けます。 このままで問題ありません。むしろこのままの方が、LAN や public IP に直接さらしにくいので安全寄りです。 

codex-web

手順 4. Mac で tailscale serve を設定する

次に、Mac の localhost 上にある codex-web を tailnet 内 HTTPS として見せます。 いまの Tailscale ドキュメントでは、ローカルポートをそのまま指定して公開できます。 

tailscale serve 8214

初回に HTTPS が未設定なら、Tailscale が有効化のための案内を出します。 設定が通ると、https://your-mac-name.your-tailnet.ts.net のような URL が表示されます。 これが iPhone から開く先です。

手順 5. iPhone を 5G でつないで URL を開く

iPhone で Wi-Fi を切るか、外出先で 5G 回線に乗った状態にします。 その上で Tailscale が接続済みになっていることを確認し、Mac 側で表示された *.ts.net の URL を Safari で開きます。

このとき、iPhone の通常の Web 通信が全部自宅 Mac 経由になるわけではありません。 Tailscale の FAQ にある通り、通常は Tailscale IP 宛てなど必要な通信だけが Tailscale 側へ流れます。 つまり「iPhone の 5G から、必要なときだけ自宅 Mac の codex-web に届く」と理解すれば十分です。

この構成で不要なもの

  • 自宅ルーターのポート開放
  • 動的 DNS の設定
  • codex-web --host 0.0.0.0 での全体公開

詰まりやすい点

  • iPhone 側で Tailscale の VPN が切れていると *.ts.net に届かない
  • iPhone は他の VPN と同時利用しづらい。Tailscale 公式 FAQ でも iOS は同時に複数の VPN を有効化できないとされています
  • Mac がスリープしているとつながらない。常時受けたいなら電源とスリープ設定も確認が必要
  • device approval や access control を厳しくしている tailnet では、iPhone の追加やサービス到達に別途承認が要る

最短の理解

やることを一文で言うと、 「Mac と iPhone を同じ tailnet に入れる → Mac で codex-web を localhost 起動 → tailscale serve 8214 で tailnet 内 URL を作る → iPhone の 5G からその URL を開く」 です。

Tailscale を使うなら

Tailscale は、参加した端末同士だけをつなぐプライベートなネットワーク tailnet を作る仕組みです。Tailscale の公式説明でも、 tailnet は public internet から直接見えない私的な空間として扱われています。

上の用語節を前提にすると、 codex-web との相性が良いのは、サーバーを無理に外へ公開せず、 ローカル専用のまま Tailscale 側でだけ到達可能にする構成です。

おすすめ構成

Host codex-web は 127.0.0.1:8214 のまま
→
Tailscale Serve localhost のポートを tailnet 内 HTTPS として中継
→
Other Devices 同じ tailnet に入った自分の PC / スマホだけがアクセス

考え方としては、次のような流れです。

1. ホストマシンで codex-web をデフォルトの localhost で起動する
2. ホストと使いたいクライアント端末を同じ Tailscale tailnet に参加させる
3. ホスト側で tailscale serve を使って 127.0.0.1:8214 を tailnet に公開する
4. クライアントは Tailscale 経由の URL で codex-web を開く
例:
codex-web
tailscale serve 8214

実運用上の利点は次の通りです。

  • codex-web 自体は localhost のままなので、LAN や public IP に直接さらしにくい
  • Tailscale 側のアクセス制御をそのまま使える
  • Tailscale Serve は tailnet 内向けで、ローカルのサービスを他の tailnet 端末に共有する用途として提供されている
  • Serve は HTTPS 証明書が必要だが、未設定なら CLI が有効化を案内する

逆に、codex-web --host 0.0.0.0 で全インターフェース待受にして Tailscale IP から入る形もできますが、設定を間違えると LAN や他の経路にも開きます。 そのため、まずは localhost のまま + tailscale serve の方が安全寄りです。

注意点として、Tailscale には Serve と Funnel があります。 Serve は tailnet 内だけ、Funnel は public internet 向けです。 codex-web を私的に遠隔利用したいだけなら、基本的には Serve を選びます。

あなたの質問への短い答え

「外のネットワークから使うなら、VPN をどうにかしないといけないよね？」に対しては、 はい、ほぼその理解で合っています。 ただし正確には「VPN が唯一の方法」ではなく、SSH トンネル や Tailscale / WireGuard のような安全な経路が必要、という理解です。
