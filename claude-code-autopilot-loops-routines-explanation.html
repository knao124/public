前提: ここでのオートパイロットは「放置」ではない

この動画で重要なのは、Claudeに大きな命令を一回投げて終わり、という話ではないことです。 Borisの構成は、session、agent、loop、routine、MCP、Computer Useを組み合わせて、仕事を小さく分け、周期的に観察し、必要な道具を使い、結果を報告させる仕組みです。

つまり、人間の役割は「次のプロンプトを書く」から「どの反復を走らせるか、どこで止めるか、何を人間レビューへ戻すかを設計する」へ移ります。

5つの部品で見るとわかりやすい

1. Session

作業の大きな単位。BorisはスマホのClaude app内で、複数のcode sessionを並行して持つと説明している。

2. Agents

session配下で具体的なタスクを担う実行者。数百から数千単位に増えることで、深い作業や探索を並列化する。

3. /loop

Claudeにcronで繰り返しジョブを作らせる仕組み。PR監視、CI修復、feedback集計のような周期作業に向く。

4. Routines

/loop のserver-side版。端末を閉じても継続するため、仕事を個人の端末寿命から切り離せる。

5. MCP / Computer Use

Salesforce、Docs、Calendar、Slackなどに接続する手段。MCPが基本で、未対応ツールはComputer Useが補う。

人間の責務

目的、権限、検証、停止条件を設計する。高リスク作業ではhuman reviewを抜かず、ループに戻す境界を決める。

オートパイロットの流れ

動画の話を実務フローに直すと、典型的には次の4つが回ります。

1. 観察 PR、CI、ログ、Slack、X、顧客フィードバック、データの時間変化を見る。
2. 周期化 1分ごと、5分ごと、30分ごと、毎日など、仕事に合った間隔で繰り返す。
3. 分担 subagentsやbatchで、修正、調査、要約、検証、報告を別々に走らせる。
4. 報告と停止 Slack、PR、issue、レポートへ戻す。権限や失敗回数で人間に返す。

具体例: PR babysitterをどう設計するか

手動運用だと、人間が毎回Claudeへ次の指示を書きます。

このPRのCI結果を見て。
失敗ログを読んで原因を推測して。
修正案を作って。
rebaseが必要ならやって。
直ったら結果をPRにコメントして。

ループ化すると、人間は次のような反復単位を作ります。

目的: 自分のPRを常にmerge可能な状態へ近づける
周期: 5分ごと
入力: GitHub PR、CI結果、失敗ログ、branch状態
Claudeの仕事: 原因分類、軽微修正、rebase、再実行、報告
許可: テスト実行、rebase、限定範囲の修正commit
停止: 2回連続失敗、仕様判断、権限不足、差分が大きい
報告: PRコメントまたはSlackに要約を送る

この構成では、人間は「次はログを見て」「次はrebaseして」と言わない。 ループが観察し、Claudeへ次の仕事を渡し、結果を見て続行か停止を決める。 Routines化すれば、端末を閉じた後も同じ監視が続く。

なぜプロンプトレスに見えるのか

  • 人間の単発プロンプトが、loopやroutineの設計へ移る。
  • Claudeがcron、MCP、Slack、GitHub、CIなどを使い、観察と報告まで自分で回す。
  • agentを大量に並べることで、調査、実装、検証、分類、報告が同時進行になる。
  • 強いモデルほど、どこで並列化すべきか、どこでloopを開始すべきかを自然に判断する。
  • 人間は細かい作業指示より、目的、制約、権限、レビュー境界を与える側へ寄る。

ビジネス上は、開発速度だけでなく防御力の前提が変わる

BorisのSaaSpocalypse論で重要なのは、すべてのSaaSが消えるという単純な話ではありません。 switching costsやprocess powerのように、移行作業や業務プロセスの複雑さで守られていた領域は、AIによって弱くなる可能性があるという話です。 一方で、network effects、scale economies、cornered resourcesのような防御力は残りやすい。

そのため、AI-nativeな新規チームは、既存企業が抱える業務変更・教育・社内抵抗なしに、最初からloopとagents前提で働ける。 ここが「小さなスタートアップが大企業と正面衝突できる」理由として語られています。

ただし、魔法ではない

オートパイロット化は、責任が消えることではありません。責任の置き場所が、個別プロンプトから運用設計へ移ります。

  • 目的が曖昧なloopは、曖昧な作業を高速に増やす。
  • 権限設計が雑だと、不要な変更や情報アクセスが発生する。
  • 停止条件がないroutineは、失敗を繰り返し続ける。
  • CI、データ、顧客情報、請求、権限変更などは、人間レビューの境界を先に決める必要がある。
  • モデルが将来より安全になるとしても、現時点の運用ではログ、差分、承認、rollback設計が必要です。

実務で試すなら、この順番

  1. 失敗しても被害が小さく、頻度が高い作業を選ぶ。例: PR監視、CI失敗分類、feedback集計。
  2. Claudeに見せる入力を固定する。例: PR URL、CIログ、直近commit、関連issue。
  3. 許可する操作を限定する。例: テスト実行、コメント作成、軽微な修正branch作成。
  4. 停止条件を先に書く。例: 2回失敗、差分が大きい、仕様判断が必要、権限不足。
  5. 報告先を決める。例: Slack、PRコメント、日次レポート。
  6. 単発promptを直すのではなく、loopの入力・周期・停止条件を直す。
