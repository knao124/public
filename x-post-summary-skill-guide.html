X投稿を要約するSkillは、何にどう接続するのか

いちばん大事なのは、SkillはXに直接ログインする部品ではない、という点です。 Skillは「どの道具でX投稿を取り、どの形で要約するか」をCodexに教える手順書です。

まず登場人物を分ける

Skill

Codex用の手順書。接続情報やAPIキーそのものを埋め込む場所ではない。

取得スクリプト

X APIやブラウザから投稿を取る実行部品。例: scripts/fetch_x_posts.py

認証情報

Xのトークン。環境変数やローカルの安全な場所から読む。Skillに直書きしない。

全体像

つまり「Xにどう接続する？」の答えは、Skillの中に接続機能を作るというより、 Skillから呼べる取得手段を用意する、です。

接続方法は大きく3つ

やりたいこと 使う接続 向いているケース 注意点
自分のホームタイムラインを読む OAuth 2.0 PKCE + /2/users/:id/timelines/reverse_chronological フォローしている人の投稿をまとめたい ユーザー認証が必要。Xアプリの「おすすめ」そのものとは違う。

投稿URLを渡して解説する場合

https://x.com/{user}/status/{id} のようなURLを渡す用途なら、 まずURL末尾の投稿IDを取り出し、GET /2/tweets/:id で1件取得します。 公開投稿を読むだけなら、基本は App-only の Bearer Token で始められます。

App-only Bearer Token。Skillの最初の実装に向く。

User Access Token。あなたのアカウントとして読める範囲を扱う。

App-onlyで始める手順

  1. X Developer Consoleに入り、Developer Accountを作る。Developer Agreementと利用目的の入力が必要。
  2. Project/Appを作る。tweet URLを読んで要約するだけなら、まずは公開データのread用途で考える。
  3. Appの Keys and Tokens を開き、Bearer Tokenをコピーする。なければAPI KeyとAPI Secretから生成する。
  4. ローカルの環境変数に入れる。SkillやGit管理ファイルには書かない。
  5. GET /2/tweets/:id で公開投稿が取れるか確認する。
# zshの現在のターミナルだけで試す
export X_APP_BEARER_TOKEN='ここにDeveloper ConsoleのBearer Token'

# 永続化するなら ~/.zshrc などに入れる。ただしGit管理ファイルには書かない。
# Developer ConsoleにBearer Tokenが表示されていない場合の生成例
# API KeyとAPI SecretはDeveloper ConsoleのKeys and Tokensから取得する
export X_API_KEY='...'
export X_API_SECRET='...'

curl -u "$X_API_KEY:$X_API_SECRET" \
  --data 'grant_type=client_credentials' \
  'https://api.x.com/oauth2/token'

返ってきたJSONの access_token がApp-only Bearer Tokenです。 それを X_APP_BEARER_TOKEN に入れて使います。

期限の考え方

App-only Bearer Tokenは、User Access Tokenのように短い有効期限で更新し続けるものではありません。 公式ドキュメント上は、同じアプリ資格情報で再発行しても、無効化されるまで同じtokenが返ると説明されています。 ただし、漏えい時の無効化、再生成、アプリ設定や権限の変更、プランやアカウント状態の影響で使えなくなることはあります。 

# 投稿URLが https://x.com/xdevelopers/status/1346889436626259968 の場合
export TWEET_ID='1346889436626259968'

curl -G "https://api.x.com/2/tweets/$TWEET_ID" \
  -H "Authorization: Bearer $X_APP_BEARER_TOKEN" \
  --data-urlencode "tweet.fields=created_at,author_id,public_metrics,entities,referenced_tweets,conversation_id,lang" \
  --data-urlencode "expansions=author_id" \
  --data-urlencode "user.fields=username,name,verified"

最初に作るならこれ

いきなり「俺のホームタイムライン全部」を狙うより、 まずは 特定アカウント群、リスト、検索クエリをAPIで取って要約 が作りやすいです。 認証が単純で、失敗原因も切り分けやすいからです。

最小構成 X_APP_BEARER_TOKEN を環境変数に置き、取得スクリプトが公開投稿をJSONで返し、Skillがそれを要約する。

Skillに書くこと

Skillは薄く保ち、実際の取得処理はスクリプトに寄せます。

x-digest/
  SKILL.md
  scripts/
    fetch_x_posts.py
1. X投稿を要約する依頼なら scripts/fetch_x_posts.py を使う。
2. トークンは環境変数から読む。Skillやリポジトリには保存しない。
3. 取得結果は、重要トピック、投稿URL、投稿者、時刻、未確認事項に分けて要約する。
4. レート制限やAPIエラーが出たら、その事実を要約に含める。

トークンごとの役割

ここが混乱しやすいところです。X APIでは「Bearer」という書き方が複数の場面で出ます。 HTTPヘッダ上はどちらも Authorization: Bearer ... ですが、 アプリとして読むトークン と あなたのユーザーとして読むトークン は別物です。

名前 正体 使う場面 Skill内の扱い
App-only Bearer Token アプリ自身としてAPIを読むためのトークン。ユーザーのログイン文脈は持たない。通常の短期アクセストークンのような期限ではなく、無効化されるまで使う前提。 公開投稿の1件取得、公開ユーザー投稿、公開検索など。tweet URLを渡して解説する最初の実装はこれ。 X_APP_BEARER_TOKEN から読む。Skillには保存しない。
OAuth 2.0 User Access Token あなたのXアカウントとしてAPIを読むためのトークン。許可したscopeの範囲で動く。 ホームタイムラインなど、ユーザー文脈が必要なAPI。保護アカウントなどは権限とAPI側の可否に依存する。 X_USER_ACCESS_TOKEN から読む。期限切れを想定する。
Refresh Token User Access Tokenを更新するためのトークン。投稿取得APIへ直接送るものではない。 長期運用でUser Access Tokenが切れたとき。OAuth 2.0の offline.access scopeが関係する。 X_USER_REFRESH_TOKEN として安全に保管し、更新処理だけで使う。
Client ID / Client Secret OAuth 2.0でアプリを識別する値。ユーザー認可フローで使う。 User Access TokenやRefresh Tokenを発行・更新するとき。 X_CLIENT_ID、必要なら X_CLIENT_SECRET。投稿取得のcurlには通常直接出さない。
API Key / API Key Secret X Developer Appの資格情報。OAuth 1.0aや一部のトークン生成で使う。 古い方式や一部のAPI操作が必要になったとき。tweet URL要約の最初の実装では主役ではない。 必要になるまでSkillからは触らない。リポジトリに書かない。 
# 公開投稿を読む最小構成
X_APP_BEARER_TOKEN=...

# 自分のアカウント文脈で読む場合
X_USER_ACCESS_TOKEN=...
X_USER_REFRESH_TOKEN=...
X_CLIENT_ID=...
X_CLIENT_SECRET=...

APIで読むときのイメージ

自分のホームタイムラインを読む場合は、ユーザー認証済みトークンで次のようなリクエストになります。

curl -G "https://api.x.com/2/users/$X_USER_ID/timelines/reverse_chronological" \
  -H "Authorization: Bearer $X_USER_ACCESS_TOKEN" \
  --data-urlencode "max_results=100" \
  --data-urlencode "tweet.fields=created_at,author_id,public_metrics,entities,referenced_tweets,lang"

公開アカウントの投稿や検索だけなら、Bearer Tokenで足りるケースがあります。 ただし、どのAPIがどの認証を許すかはエンドポイントごとに違います。

現実的な作り方

  1. まずは読む対象を決める。例: 特定アカウント、検索語、自分のホームタイムライン。
  2. 必要なX Developer Appを作り、必要なトークンを環境変数に入れる。
  3. scripts/fetch_x_posts.py で投稿をJSONとして取れるようにする。
  4. SKILL.md で、そのスクリプトの使い方と要約フォーマットをCodexに教える。
  5. レート制限、APIコスト、取得できなかった投稿を要約に明記させる。

注意点

  • X APIは無料で何でも読める前提ではありません。現在は利用量に応じた課金とエンドポイントごとの制限があります。
  • SkillにAPIキーやトークンを書かないでください。漏れるとアカウントや課金に影響します。
  • ブラウザ操作でXを見る方法は最後の手段です。動きやすいが壊れやすい、という性質があります。
  • 要約結果には投稿URLや時刻を残すと、あとから確認しやすくなります。

App-onlyで詰まったとき

症状 よくある原因 見るところ
401 Unauthorized Bearer Tokenが間違っている、失効している、環境変数が空。 echo ${X_APP_BEARER_TOKEN:0:8} で値が入っているか確認し、Developer Consoleで再生成。
403 Forbidden App-onlyでは読めないAPIを呼んだ、またはプラン/権限が足りない。 そのエンドポイントがapplication-only auth対応か、X APIのプランで使えるか確認。
429 Too Many Requests レート制限。App-onlyの制限枠を使い切っている。 時間を空ける。Skillには取得失敗とレート制限を明記させる。
投稿が取れない 投稿削除、非公開、年齢/地域/ログイン文脈が必要、URLからID抽出ミス。 投稿IDが数字だけか確認。必要ならUser Access Tokenかブラウザ操作に切り替える。

参照元

  • X API Timelines: ホームタイムライン、ユーザー投稿、メンション取得の違いを確認。
  • Get Post by ID: 投稿URLから抜いたIDで1件取得するAPIを確認。
  • App-only authentication: App-only Bearer Tokenがユーザー文脈を持たないことを確認。
  • Getting Access: Bearer Token、Client ID、Client Secretの役割分担を確認。
  • OAuth 2.0 Authorization Code with PKCE: ユーザー認証、scope、refresh tokenの扱いを確認。
  • Search recent Posts: 直近検索エンドポイントの用途を確認。
  • Rate Limits: エンドポイントごとの制限があることを確認。
