資料の流れを復元する

ガイドは、LangWatchがOTLP endpointを提供し、OpenTelemetry SDKからtraceを受けられることを説明します。Pythonだけでなく、Javaや.NETなど任意言語から送れる点が強調されます。

導入手順は、SDKを入れる、OTLP exporter endpointをLangWatchへ向ける、API keyをheaderに入れる、TracerProviderを初期化する、LLM callやagent処理をinstrumentする、という流れです。

この資料の価値は、LangWatch専用SDKだけに閉じないことです。すでにOpenTelemetryを使っている組織なら、collectorやexporterの設定でLangWatchへ追加送信できます。

さらに、OpenInferenceやOpenLLMetryのようなinstrumentationで出したtraceをLangWatch側のevaluationやsimulationに接続できます。

何が学べるか

既存のobservability stackを捨てずに、agent評価基盤を追加できることが学べます。評価のためだけに別ログ形式を作ると、開発者が見るtraceと評価器が読むtraceが分裂します。

また、OTel Collectorの重要性が分かります。collectorを挟めば、LangWatchには評価に必要なtraceだけを送り、通常監視backendにはmetadata中心で送る、といったroutingができます。

LangWatchでscenarioやsimulationと結びつけるためには、trace属性にscenario id、eval set id、prompt version、model versionを入れる必要があります。これはガイド単体には細かく書かれていなくても、実務導入では必須です。

Agent自動QAへ落とす手順

まずstaging環境のagent traceをLangWatch projectへ送ります。本番より先にstagingでschemaを安定させることで、PIIや容量の問題を避けられます。

次に、LangWatch側でscenarioやevalとtraceを関連付けます。CI run idやscenario idをspan属性に入れておけば、失敗したシナリオのtraceをすぐ見られます。

最後に、本番traceはsamplingとredactionを強めます。すべてを送るのではなく、error、low rating、高cost、高latency、guardrail hitなどのtraceを評価キューへ送る方が現実的です。

注意点

OTelへ送れば自動で評価できるわけではありません。traceにsemantic attributesがなければ、評価器は最終回答程度しか見られません。

任意言語対応は強みですが、言語ごとにSDKやexporterの挙動は違います。sample traceを固定し、期待span treeと属性が出ているかを最初に検査するべきです。

OTel pipelineからLangWatchへ流す運用設計

LangWatchのOTel integrationは、既存のOpenTelemetry運用を評価基盤へ接続するための入口です。直接SDKから送ってもよいですが、実務ではCollectorを挟む方が安全です。Collectorでredaction、sampling、routing、attribute normalizationを管理できます。

評価に必要なtrace属性は、LangWatchへ送る前に揃えます。scenario id、eval set id、prompt version、model version、agent version、deployment environmentがないと、後で評価結果を比較できません。

本番traceをそのまま全送信するのではなく、error、user low rating、高cost、高latency、guardrail hitのような条件で評価用プロジェクトへ流す設計が現実的です。stagingでは全文capture、本番ではmetadata中心にします。

実装チェックポイント

  • OTLP endpointとAPI keyを環境変数化する
  • CollectorでPII redactionを行う
  • scenario idとeval set idをroot spanへ入れる
  • productionはsamplingとroutingを強める
  • LangWatch側のsimulation結果とtrace idを紐づける
