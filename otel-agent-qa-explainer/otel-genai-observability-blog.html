読む前の地図

GenAI semantic conventionsを読んだ直後に読むと、属性名とspan treeが実際の開発体験でどう役立つかが分かります。QA基盤の前に、まずtrace viewerで何を見るべきかを掴めます。

この解説は、動画解説記事と同じ方針で、資料の順序、主張、具体例、実装への落とし込みを追えるように作っています。著作権上、本文全体の再掲ではなく、短い引用と詳細な言い換えで構成しています。

短い根拠引用

without observability, you are guessing

agentが遅い・失敗した原因をtraceなしに推測する危うさを示す短い表現。

記事の流れを復元する

記事は、agentが45秒かかったときに、どこで時間を使ったのか分からないという問題から始まります。LLMが遅かったのか、tool callが遅かったのか、retry loopに入ったのか、promptが巨大化したのかは、最終レスポンスだけでは判断できません。

次に、OpenTelemetry GenAI semantic conventionsを使って、agent実行をtrace、metrics、structured logsとして観測する例を示します。top-levelにはagent invocationがあり、その下にchat/inference spanやexecute_tool spanがぶら下がります。

具体例としてVS Code CopilotやAspire Dashboardが出てきます。ローカルでOTel信号を出し、dashboard上でspan tree、duration、tool call、tokenなどを確認する流れです。これは本番監視だけでなく、開発時のinstrumentation確認にも使えます。

記事はまた、content captureがデフォルトでは無効である点に触れます。promptやtool argumentsを見たいなら明示的に有効化する必要がありますが、機密情報を含むため慎重に扱う必要があります。

この資料から得られる実務感覚

第一に、trace viewerは評価器を作る前の探索道具です。いきなりCI gateを書くのではなく、まず人間がtrace treeを見て、どのspan名と属性が安定しているかを確認します。

第二に、agentの遅延は単一のdurationではなく、spanの分布として見るべきです。LLM callが遅い、retrievalが遅い、toolが遅い、同じtoolを繰り返している、retryが走っている、という原因ごとに対策が変わります。

第三に、content captureはQAの精度とsecurityのトレードオフです。回答品質を評価するにはpromptやtool resultが必要なことが多い一方、それをどこまでtelemetryに入れるかは環境別に決める必要があります。

Agent自動QAへ落とすなら

このブログの実例をQAに置き換えると、まずローカル・ステージングでagentの代表シナリオを走らせ、trace viewerで期待したspan treeが出ているか確認します。root spanがない、tool spanがchildになっていない、argumentsが欠ける、errorがstatusに出ない、といった問題をここで潰します。

次に、trace viewerで見た検査観点をassertionに変えます。たとえば、指定シナリオでは`execute_tool`が1回だけ発生する、durationが5秒未満、tokenが閾値内、error.typeが空、retrieval spanが生成spanの前にある、などです。

最後に、trace idをPR番号、commit SHA、scenario idと結びつけます。こうしておけば、どの変更でagentの経路が変わったかを後から追えます。

注意点

記事の例は可視化が中心であり、評価器そのものの作り方は詳しくありません。CIで合否判定するにはTracetest、AgentEvals、LangWatch、Phoenix evalなどを組み合わせます。

また、coding assistant系のtraceはframeworkや拡張機能の都合でshapeが変わることがあります。AgentEvalsのような評価ツールへ直接食わせる前に、実際のspan構造を確認する必要があります。

trace viewerからCI評価へ変換する手順

このブログの価値は、trace viewerの観察をCI評価へ変換する中間手順が見えることです。最初はdashboardでspan treeを見て、agent invocationの下にどのspanが出ているか確認します。次に、安定して出ているspan名と属性だけを評価器の入力にします。

たとえば、遅延が問題なら、LLM span、tool span、retrieval spanそれぞれのduration分布を見ます。tool retryが問題なら、同一tool nameの連続回数やerror.typeを見ます。costが問題なら、token usageとmodel nameを見ます。こうした観察を、そのままthresholdやassertionへ落とします。

content captureを有効にするかどうかは、評価可能性と安全性の境界です。回答内容やtool argumentsを見なければ品質判定できない一方、ソースコードや秘密情報がtraceへ入る危険があります。CIでは人工データ、本番ではredaction後metadata、という分け方が実務的です。

実装チェックポイント

  • local dashboardでroot spanとchild spanの親子関係を確認する
  • 評価器に使うspan名をdashboard上で実測して固定する
  • 遅延、retry、token、errorを別々の評価項目にする
  • trace idをCI run、commit SHA、scenario idへ紐づける
  • content capture有効化前にsecret混入経路を確認する
