built on top of OpenTelemetry

OpenLLMetryがOTel上に作られた計測層であることを示す短い表現。

資料の流れを復元する

資料は、OpenLLMetryをLLM applicationのobservabilityを得るためのOSSとして説明します。LLM frameworkを使っていても、foundation model APIを直接呼んでいても、実行をtraceとして記録することが目的です。

OpenLLMetryはTraceloopのbackendへ送ることもできますが、OTel互換exporterを使って既存のobservability backendへ送ることもできます。これは、AI専用の島を作らず、既存のサービス監視とつなげる設計です。

実装面では、初期化処理とdecoratorが中心です。workflowやtaskを明示的に区切ることで、LLM callだけでなく、アプリケーション内の処理単位もspan treeとして可視化できます。

Tracetestの記事では、このtraceをテストの検証対象にします。つまりOpenLLMetryは評価器ではなく、評価器が読む証跡を作る役割です。

何が学べるか

LLM appの品質問題は、model APIの応答だけでは説明できません。prompt template、retrieval、tool call、post-processing、guardrail、API responseの各段階があり、OpenLLMetryはその段階をspanとして見せるための入口になります。

また、workflow decoratorの名前は評価単位になります。demoでは短い名前でもよいですが、実務では`refund_policy_answering`、`incident_triage`、`quote_generation`のように、QAシナリオと対応する名前にするべきです。

既存のOTel pipelineへ送れるため、LLM appのtraceと通常backendのHTTP、DB、queueのtraceを同じtransactionとして見られます。agentがtoolを呼び、そのtoolがDB更新したかまで追えることが自動QAには重要です。

実装に落とす手順

まずアプリ起動時にOpenLLMetryを初期化し、service name、environment、exporter endpointを固定します。CI、staging、productionでenvironmentを分けることで、評価用traceと本番traceを混同しにくくします。

次に、workflowとtaskを明示します。LLM callだけが見えても、agentがどの業務段階にいたかは分かりません。intent分類、retrieval、tool selection、final answer generationなどを区切ります。

最後に、Tracetestや独自assertionでspanを検査します。たとえば、特定workflowではretrieval taskが必ず実行される、tool callが1回だけ発生する、openai.chat spanがerrorになっていない、といった検査です。

注意点

OpenLLMetryを入れただけでは評価基準は生まれません。traceをどう読み、何を合格とするかは別に設計する必要があります。

また、promptやresponseのcaptureを有効にする場合は、本番データの機密性に注意が必要です。CI用の人工データと本番traceでは保存方針を分けるべきです。

OpenLLMetryを既存監視とQAへつなぐ設計

OpenLLMetryは、LLM appを既存のOpenTelemetry pipelineへ載せるための実装層として読むと分かりやすいです。LLM callだけを個別ログに出すのではなく、通常のHTTP requestやDB spanと同じtraceに含めることで、agentの外部副作用まで追えるようになります。

workflow decoratorは単なる可視化ラベルではなく、評価単位です。たとえば`incident_triage` workflowの中でclassification、retrieval、tool execution、report generationをtaskとして分ければ、どの段階が壊れたかを自動評価できます。

Tracetestと組み合わせる場合、OpenLLMetryで出したspanに対して、prompt template spanがある、openai chat spanが成功した、tool spanが1回だけ出た、というassertionを書きます。意味品質は別評価器に任せ、実行経路はtraceで厳密に見ます。

実装チェックポイント

  • workflow名は業務フロー名にする
  • task名は評価器が読む安定した名前にする
  • CI/staging/productionでservice.versionとenvironmentを分ける
  • LLM callと下流HTTP/DB spanを同じtraceで相関させる
  • prompt/response captureは人工データ環境から始める
