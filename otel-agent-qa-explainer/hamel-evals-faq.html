短い根拠引用

Start with error analysis, not infrastructure

eval基盤より先に失敗分析を行うべきだという中心思想を示す短い表現。

資料の流れを復元する

FAQの中心思想は、evalをインフラから始めないことです。まず実際の出力やtraceを人間が読み、何が失敗しているかを言語化します。genericなhelpfulness scoreから始めるのではなく、実際の失敗分類から評価器を作ります。

次に、20から50件、必要なら50から100件程度のtraceを読み、open-ended notesを残します。最初からラベルを固定せず、失敗の型を観察します。tool未使用、wrong tool、context loss、tone mismatch、missing approval、stale retrievalなどです。

その後、失敗分類をbinary failure modeへ落とします。たとえば「注文番号が会話内にあるのにlookup toolを呼ばない」「SQL生成後に実行前確認をしない」のように、修正可能な単位へ分解します。

最後に、自動評価器を作ります。regexやschema validatorで捕まるものは安く作り、意味判断が必要なものだけLLM-as-Judgeに任せます。multi-turn traceでは、最終失敗ではなく最初の上流失敗を探すことが重視されます。

何が学べるか

最大の学びは、evalは観察から始まるということです。ツールやダッシュボードを先に作ると、何を測るべきかが曖昧なままになります。

また、custom evaluatorの重要性が分かります。hallucination、helpfulness、faithfulnessのような汎用指標だけでは、業務固有の失敗を捕まえられません。

multi-turn workflowでは、transition failure matrixの考え方が有効です。どの状態からどの状態への遷移で失敗するかを集計すると、修正すべき箇所が見えます。

Agent自動QAへ落とす手順

まず本番またはステージングtraceをサンプリングします。成功例、失敗例、低評価、高cost、高latencyを混ぜます。

次に人間がtraceを読み、最初の失敗点にラベルを付けます。分類、retrieval、tool selection、tool arguments、policy decision、generation、handoffのどこで壊れたかを見ます。

その後、上位の失敗分類から評価器を作ります。頻度が高く、修正可能で、業務影響が大きい失敗を優先します。

最後に、評価器の精度を人間ラベルと照合します。LLM judgeは特に、定期的なcalibrationが必要です。

注意点

LLMに失敗分類を任せきると、業務固有の重要な失敗を一般的なカテゴリへ丸めてしまうことがあります。人間のerror analysisを省略しない方がよいです。

100% passを目指す評価は危険です。簡単すぎるevalは安心感だけを生みます。実際の失敗を捕まえ、改善後に失敗率が下がる評価が価値のある評価です。

error analysisから評価器へ変換する

このFAQをagent QAに適用すると、最初の作業はツール選定ではなくtrace読解です。20から50件のtraceを読み、自由記述で失敗メモを残します。この段階ではラベルを固定しすぎず、実際の失敗語彙を拾います。

次に、失敗メモを修正可能なfailure modeへ変換します。`回答が微妙`ではなく、`ユーザーが注文番号を出したのにlookup toolを呼ばない`、`承認前にwrite toolを呼ぶ`、`retrieval結果にない断定をする`のように書きます。

最後に、failure modeごとに最も安い評価器を選びます。regexやschemaで済むものはLLM judgeにしない。LLM judgeが必要な場合も、人間ラベルと一致するかを定期的に測ります。

実装チェックポイント

  • 最初の20から50 traceは人間が読む
  • 失敗分類は修正可能な単位にする
  • 最初の上流失敗にラベルを付ける
  • 汎用metricよりcustom evaluatorを優先する
  • LLM judgeは人間ラベルでcalibrationする
