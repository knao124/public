記事の流れを復元する

記事は、LLM appのテストが最終レスポンスだけでは不十分であるという問題から始まります。LLM APIが呼ばれたか、prompt templateが使われたか、LangChainのchainが期待通り走ったかはresponseだけでは分かりません。

次に、OpenTelemetry SDKとOpenLLMetryを使ってLLM appをinstrumentします。これにより、ChatPromptTemplateやopenai.chatのような内部処理がspanとして見えるようになります。

Playwrightは外側のtriggerとして使われます。API endpointやUIを叩き、実際のアプリケーション実行を発生させます。その実行で生成されたtraceをTracetestが取得し、span assertionを行います。

記事のポイントは、テストを二層にすることです。外側ではアプリがユーザーに応答することを確認し、内側では期待したLLM workflowが実際に通ったことをtraceで確認します。

Agent QAへの読み替え

agent UIをQA agentやPlaywrightで操作しても、それだけでは裏側のagentが何をしたか分かりません。trace-based testingを組み合わせると、UI操作と内部tool callを同じテストで検査できます。

たとえば、チャットUIに質問を投げ、traceでintent classification、retrieval、execute_tool、final generationを確認します。最終回答が正しそうでも、retrievalを使っていないなら失敗にできます。

この構成は、agentに自動QAさせる場合にも有効です。QA agentが画面上で検査した結果と、agent-under-testのOTel traceを突き合わせれば、表面上の動作と内部経路の両方を保証できます。

実装手順

まずLLM appへOpenLLMetryやOpenInferenceを入れ、OTLP exporterを設定します。ローカルではJaegerやTracetest、CIではcollector経由のbackendへ送ります。

次にPlaywrightやAPI testで代表シナリオを実行します。実行時にtrace idやtest run idをrequest headerまたはspan属性に入れ、対象traceを引けるようにします。

最後にTracetestでspan assertionを書きます。prompt template spanが存在する、openai.chat spanが成功している、tool spanが期待通り、error spanがない、durationが閾値内、という検査です。

注意点

framework内部のspan名に依存しすぎると壊れやすくなります。業務上重要なstepには自前で安定spanを足すべきです。

CI artifactとしてtraceを保存するなら、promptやtool resultにsecretや顧客情報が混ざらないよう、人工テストデータとredactionを徹底します。

外部E2Eと内部trace検査を一つにする

この記事の実装型は、agent QAでそのまま使えます。PlaywrightやAPI testで外から実際のユーザー操作を発生させ、その実行で生成されたtraceをTracetestで検査します。これにより、UIは動いているが内部ではretrievalを使っていない、という失敗を捕まえられます。

LLM appでは、prompt template、LLM call、tool call、post-processingがすべて品質に関わります。外側のresponse testだけでは、どの部品が実行されたか分かりません。trace-based testingは、内部経路をE2Eテストの一部にします。

CIでは、失敗したときにPlaywrightのスクリーンショット、Tracetestのassertion結果、OTel trace JSONを一緒に保存します。LLM appの失敗はログ一行では追えないため、調査導線が重要です。

実装チェックポイント

  • 外部testからtrace idを渡すか、root spanにtest idを入れる
  • UI/APIの成功とspan assertionを両方見る
  • prompt template、LLM call、tool callを別々に検査する
  • 失敗時artifactにtrace JSONを残す
  • 意味評価は別のjudgeに分担させる
