短い根拠引用

using trace data as test specs

Tracetestの中心思想を示す短い表現。

資料の流れを復元する

Tracetestの基本思想は、テストの合否をHTTP responseだけで判断しないことです。requestによって発生したdistributed traceを取得し、そのtraceに含まれるspanや属性を検査します。

triggerにはHTTP、gRPC、messageなどが使えます。テスト実行後、trace backendから該当traceを取得し、span selectorで対象spanを選び、assertionを評価します。

assertionの対象は、spanが存在すること、属性が期待値であること、durationが閾値内であること、errorがないこと、DBやqueueなどの下流処理が発生したこと、または発生していないことです。

UIやYAMLでテスト定義を管理でき、CIから実行できます。つまり、traceに基づく品質ルールをコードレビュー可能な形で管理できます。

Agent QAでの読み替え

agentに置き換えると、tool callや外部副作用がassertion対象になります。たとえば、顧客情報更新agentであれば、承認前にwrite APIが呼ばれていないこと、承認後に正しいendpointが1回だけ呼ばれることを検査できます。

LLM judgeではなくspan assertionで確認できることは多いです。tool spanの存在、tool名、引数、error.type、duration、DB write、queue publish、HTTP statusは決定的に検査できます。

安全性QAでは、回答が自然かどうかより、危険な副作用が起きていないかが重要な場合があります。Tracetestの発想はこの領域に強いです。

実装手順

まずagentの外側からシナリオを実行します。チャットAPI、UI操作、workflow triggerなど、実際の入口を使います。

次に、実行とtraceを結びつけるためにscenario idやtest run idをroot spanに入れます。これがないと、CIで生成されたtraceを確実に引けません。

最後に、span selectorとassertionをYAML化します。`execute_tool` spanが存在する、`tool.name`が期待値である、`http.status_code`が200、`db.operation`が発生しない、durationが閾値以内、といったルールです。

注意点

Tracetest単体では意味品質や会話満足度は評価しにくいです。最終回答の妥当性はPhoenix、LangWatch、AgentEvals、LLM-as-Judgeなどと組み合わせます。

span名やselectorをframework内部名に寄せすぎると、upgradeでテストが壊れます。業務上変わってはいけないspanには安定した名前と属性を付けます。

trace assertionをagent安全性に使う

Tracetestの考え方をagentへ適用すると、最も価値が出るのは副作用の検査です。LLM judgeは回答文を採点できますが、承認前にwrite APIを呼んだか、DB更新が発生したか、queue publishが何回あったかはtrace assertionの方が確実です。

agentの危険な行動は、最終回答に現れないことがあります。ユーザーには「更新しました」と言わなくても、裏側でwrite toolを呼んでいる可能性があります。trace assertionなら、この種の隠れた副作用を検出できます。

assertionは実装詳細ではなく業務契約に寄せます。`SomeFrameworkToolNode`ではなく、`app.tool.customer_update`のような安定span名にし、tool.nameやapproval.statusを属性として見る方が保守しやすいです。

実装チェックポイント

  • root spanにtest run idを入れて対象traceを特定する
  • 禁止副作用をnegative assertionとして書く
  • tool call数、HTTP status、DB write、queue publishを検査する
  • durationやretryを運用リグレッションとして見る
  • span selectorをframework内部名へ寄せすぎない
