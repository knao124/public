資料の流れを復元する

この資料は、agent評価を散らばったスクリプトではなく、宣言的な仕様として管理する考え方を示します。EVAL.yamlのようなファイルに、テストケース、評価器、rubric、期待行動を書き、agentの品質基準をコードレビューできる形にします。

評価器は一種類ではありません。code judgeは決定的に検査できる条件、LLM judgeは意味判断、rubricは採点基準の明文化、tool trajectoryはtool使用の妥当性、field accuracyは構造化出力、execution metricsはlatencyやcostを担当します。

資料の狙いは、agent品質を主観的な印象から、明示された評価契約へ移すことです。開発者、QA担当、ドメイン専門家が同じ評価ファイルを読み、期待されるagent behaviorを議論できるようにします。

この仕様は特定frameworkの実装手順というより、評価をどう構造化するかの設計資料として読むべきです。

何が学べるか

第一に、agent評価は最終回答だけで構成しないことです。tool trajectory、field accuracy、execution metricsを含めることで、回答が自然でも内部経路や運用コストが悪いケースを検出できます。

第二に、評価基準はPRレビュー可能なファイルにするべきです。promptやtool schemaを変更したなら、それに対応するevalも同じPRで変わるべきです。

第三に、rubricは抽象語ではなく、業務条件へ落とす必要があります。helpfulではなく、返金条件、期限、次の行動を含む、のように書くと修正可能になります。

Agent自動QAへ落とす手順

まずagentの重要フローごとにeval fileを分けます。返金、注文変更、障害対応、予約変更のように、業務単位でファイルを分けるとレビューしやすくなります。

次に、評価器を混ぜます。tool使用はtrajectory evaluator、構造化出力はfield evaluator、危険な副作用はcode evaluator、回答品質はLLM judgeに分けます。

最後に、eval resultにはeval file version、judge prompt version、model version、scenario idを残します。評価基準自体が変わったとき、過去結果と比較できるようにするためです。

注意点

宣言的な仕様は読みやすい一方、裏側の評価器が曖昧だと合否は不安定になります。LLM judgeは人間ラベルとの整合性を定期的に確認する必要があります。

仕様ファイルを増やすこと自体を目的にしないでください。実際に起きた失敗、または業務上致命的な失敗からevalを作る方が保守できます。

EVALファイルをどう育てるか

Agent Evals仕様を運用するなら、EVALファイルはテストケースの置き場ではなく品質契約です。agentの期待行動、評価器、rubric、threshold、metricを明示し、promptやtool変更と一緒にレビューします。

最初のEVALファイルは、網羅表ではなく失敗再発防止から作るのがよいです。実際に起きた事故や低評価traceを一つ選び、それを防ぐtool trajectory、field accuracy、code judgeを追加します。

評価器の混ぜ方が重要です。構造化出力やtool callはdeterministic evaluator、文章品質や説明の十分性はLLM judge、運用負荷はexecution metricsに分けます。全部をLLM judgeにすると不安定で高コストになります。

実装チェックポイント

  • 評価ファイルを業務フロー単位で分ける
  • rubricは抽象語ではなく観測可能な条件で書く
  • judge promptとjudge modelをversion管理する
  • threshold変更はPRで明示する
  • 実際の失敗traceからevalを増やす
