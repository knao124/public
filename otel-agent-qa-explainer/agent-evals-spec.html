読む前の地図

このページでは、資料の主張をそのまま要約するだけでなく、OpenTelemetry traceを使ったagent自動QAへどう接続するかを中心に整理します。

読み方は、まず資料が扱う単位を確認し、次にQA基盤での役割、最後に実装時の注意点を見る順序です。

まず、この資料は何を言っているか

この資料の核は、agent評価を個別スクリプトの寄せ集めにせず、宣言的な仕様として管理することです。EVAL.yamlにテスト、評価器、rubric、期待行動を書き、agentの品質基準をコードレビュー可能な形にします。

評価タイプは複数あります。決定的なcode judge、意味評価のLLM judge、採点基準を明文化するrubric、tool使用の妥当性を見るtool trajectory、構造化出力を見るfield accuracy、latencyやtokenを見るexecution metricsです。

この仕様は、どのagent frameworkを使うかよりも、何を合格とみなすかを中心に置きます。QA担当、ドメイン専門家、開発者が同じ評価ファイルを読めるようにするのが狙いです。

自動QAにどう組み込むか

実務では、評価仕様をリポジトリ内に置き、promptやtool仕様の変更と同じPull Requestで更新します。agentの期待動作が変わったなら、実装だけでなくEVAL.yamlも変わるべきです。

評価タイプを混ぜるのがポイントです。例えばサポートagentなら、tool trajectoryで顧客検索toolの呼び出しを確認し、field accuracyでticket labelを確認し、LLM judgeで返信文の丁寧さを評価します。

execution metricsは軽視されがちですが、agent QAでは重要です。正しい回答でも、tokenが倍増した、toolを過剰に呼んだ、latencyが閾値を超えた、という回帰は本番運用で問題になります。

評価ファイルの粒度

1つの巨大な評価ファイルにしない方が運用しやすいです。agentの機能単位、tool単位、失敗モード単位で分けると、PRレビュー時に何が変わったかが追いやすくなります。

rubricは抽象語だけで書かないことが重要です。「helpful」ではなく「返金条件、期限、次の行動の3点を含む」のように、失敗時に修正方針が見える基準にします。

LLM judgeのpromptもバージョン管理します。judge promptが変わるとscore分布が変わるため、model version、judge version、eval file versionをtraceや結果に残すと比較がしやすくなります。

注意点

宣言的な仕様は読みやすい一方、裏側の評価器が曖昧だと合否が不安定になります。特にLLM judgeは人間ラベルとの整合性を定期的に確認する必要があります。

仕様を整えること自体が目的化しないよう、最初は実際に起きた失敗を再発防止する評価から追加するのがよいです。網羅表を先に作りすぎると、保守できない評価群になりがちです。
