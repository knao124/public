READMEの流れを復元する

READMEは、sample traceとeval setを使ったQuick Startから始まります。traceはagentが実際に行った行動列で、eval setは期待される行動や採点基準です。CLIで両方を渡すと、metricごとのscoreが返ります。

次に、tool trajectoryの評価が説明されます。Helm agentの例のように、正しいtoolが呼ばれたか、順序が合っているか、期待されないtoolが混ざっていないかを採点します。

CLIはofflineでtrace fileを評価できます。一方、serve modeやWeb UIを使うと、trace treeを見ながら評価できます。MCP serverとしてAI assistantから呼ぶ構成も示されています。

FAQでは、対象範囲への注意があります。AgentEvalsは、OTel GenAI traceをきちんと出すpurpose-built agentに向いており、長時間のcoding agent session全体をそのまま評価する用途とは限りません。

何が学べるか

READMEから学べるのは、評価のI/O契約です。入力はtraceとeval set、出力はmetric scoreと失敗理由です。この契約が明確ならCIに載せられます。

custom evaluatorを標準入出力で作れる点も重要です。業務固有の評価をPython、TypeScript、社内ライブラリ、SQL検査などで実装し、AgentEvalsの評価パイプラインへ組み込めます。

また、coding agent評価への慎重な記述から、trace schemaの重要性が分かります。すべてのagent telemetryがそのまま評価可能なGenAI span treeになっているわけではありません。

CI導入手順

第一に、PRごとに小さな代表シナリオを実行し、trace JSONをartifactとして保存します。

第二に、eval setをリポジトリに置きます。期待tool、trajectory match type、最終回答条件、metric thresholdを定義します。

第三に、CLIを実行し、threshold未満ならCIをfailにします。失敗時はeval result JSONとtrace viewerリンクをPRに添えると、開発者がすぐ原因を追えます。

第四に、production incidentからtraceを取り込み、eval setへ追加します。これにより、実際に起きた失敗が回帰テストになります。

注意点

tool trajectory中心の評価は、tool選択が重要なagentでは強力ですが、文章品質や曖昧なユーザー満足度は別評価が必要です。

traceにpromptやtool resultを含める場合、CI artifactとして外部に見える可能性があります。公開リポジトリでは特に、テストデータとredactionを厳密に管理してください。

CLI導入時の運用手順

GitHub READMEから実務導入へ移すなら、最初にsample traceとsample eval setを自社agentのtraceへ置き換えます。評価器を先に作るより、実際のtrace shapeを見て、どのmetricが使えるか確認します。

CIでは、agent scenario run、trace保存、agentevals run、threshold判定、artifact保存の順にします。失敗時には、scoreだけでなく、どのspanが期待と違ったかを表示します。

custom evaluatorは早めに用意すると価値が出ます。たとえば、社内ポリシーIDが回答に含まれるか、ticket labelが正しいか、SQL実行前確認があるか、などは標準metricだけでは表現しにくいからです。

実装チェックポイント

  • sample traceを自社traceで置き換える
  • eval setを小さく始める
  • thresholdでCIをfailにする
  • 失敗traceとeval resultをartifactに残す
  • coding agent全体評価には専用変換が必要か確認する
