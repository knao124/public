記事の流れを復元する

記事は、agent定義、runtime、observabilityを分離する構成から始まります。Agent Specにはtools、system prompt、model設定などを記述し、runtimeはそのspecを実行します。Phoenixは実行結果をtraceとして受け取り、観測と評価を担当します。

次に、同じagent specを複数runtimeで動かす例が出ます。LangGraphとWayFlowのように実行エンジンが違っても、Agent Specで定義された同じagentを動かし、Phoenixへtraceを送れます。

その後、captured tracesに対してprogrammatic evaluationを行います。code-based evaluatorで形式や必須項目を検査し、LLM-as-Judgeで調査の完全性や回答品質を評価する、という分担です。

最後に、runtime比較の意味が明確になります。最終回答が似ていても、tool呼び出し回数、retry、latency、cost、失敗spanの数が違う場合があります。traceがあれば、runtime移行の安全性を定量的に比較できます。

何が学べるか

第一に、agent definitionをruntimeから切り離す価値が分かります。promptやtool registryをspec化しておけば、runtimeを変えても同じシナリオと評価基準で比較できます。

第二に、評価はcode-based evaluatorとLLM judgeを混ぜるべきだと分かります。出力が空でない、incident report形式を含む、toolで集めたデータに言及する、といった条件は決定的に検査できます。一方、調査が十分か、回答が実務的かはLLM judgeが向いています。

第三に、trace属性としてruntime名、agent spec version、tool registry versionを残す重要性が分かります。同じシナリオでWayFlowだけretryが増える、といった分析ができるからです。

Agent自動QAへ落とす手順

まず、agentの入力セットと期待評価をruntime非依存に定義します。入力、期待されるtool、期待する出力形式、重要な業務条件を一つのeval harnessにまとめます。

次に、複数runtimeで同じシナリオを実行し、traceをPhoenixへ送ります。traceにはruntime、commit SHA、agent spec version、prompt version、model versionを必ず入れます。

最後に、評価結果を横比較します。final scoreだけでなく、tool call count、LLM call count、latency、token、error span、retry countも見ることで、runtime移行の隠れたコストを検出できます。

注意点

runtimeが違うとspan粒度や親子関係が微妙に異なることがあります。評価器を書く前に、runtimeごとのtrace shapeをnormalizeする必要があります。

LLM-as-Judgeでruntime比較をする場合、judgeのばらつきが結果に見える可能性があります。重要な比較では同じjudge model、同じjudge prompt、同じtemperature、同じtrace snapshotで評価します。

runtime比較を評価可能にする設計

このブログを実装へ移すときの中心は、agent definition、runtime、evaluation harnessを分けることです。Agent Specにtool、prompt、model設定を置き、runtimeはそれを実行し、Phoenixはtraceと評価を担当します。これにより、runtime変更がagent品質へ与える影響を測れます。

比較時に見るべきなのはfinal answerだけではありません。tool call count、LLM call count、retry、latency、token、error span、retrieval回数を並べると、表面上は同じ回答でも運用コストや安定性が違うことが分かります。

programmatic evaluationは二段階に分けます。まずcode evaluatorで必須形式と必須行動を検査し、次にLLM judgeで調査の十分性や説明品質を採点します。runtime比較では、judge条件を固定しないと差分がjudgeの揺れに見えてしまいます。

実装チェックポイント

  • agent spec versionをtrace属性に入れる
  • runtime名とruntime versionをtrace属性に入れる
  • 同じinput setを複数runtimeで実行する
  • final score以外にcost、latency、retry、tool countを比較する
  • judge promptとjudge modelを固定して比較する
