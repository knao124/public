まず、この資料は何を言っているか

OpenInferenceは、OpenTelemetryだけでは表現しにくいAIアプリの文脈を補うものです。LLM invocationだけでなく、retrieval、vector store、external tool、agent frameworkの活動をtraceに載せるためのconventionsとpluginsを提供します。

PythonだけでもOpenAI、OpenAI Agents、Claude Agent SDK、LangChain、LlamaIndex、CrewAI、Google ADK、AutoGen、PydanticAI、smolagentsなど、多数のinstrumentationが並んでいます。

重要なのはbackend非依存性です。Phoenixで使いやすい一方、OpenTelemetry-compatible backendに送れるため、既存のobservability stackとつなげやすいです。

自動QAでの役割

OpenInferenceは、自動QAの「センサー層」です。評価器そのものではなく、評価に必要な材料をtraceとして揃える役割を担います。

agent QAでは、frameworkごとにログ形式がばらけると評価器が増殖します。OpenInference instrumentationを入れてspan kindや属性を揃えれば、Phoenix、AgentEvals、LangWatch、独自notebookなど複数の評価面で同じtraceを使えます。

特にRAG agentでは、retriever spanとLLM spanの接続が重要です。どのqueryでどのdocumentが取られ、そのcontextがどのgenerationに渡ったかが見えると、grounding評価やirrelevant retrieval検出ができます。

導入時の実務要点

まず自分たちのagent frameworkに対応instrumentationがあるかを確認します。あれば自動計測で始め、agent固有のdecision pointだけmanual spanを追加します。

span属性名は評価器の入力契約です。後から名前を変えると過去traceとの比較が壊れます。導入時に、trace id、session id、user cohort、prompt version、model version、tool name、tool arguments policyを決めます。

複数backendに送る場合は、OTel Collectorを挟むと運用しやすいです。評価用backendと通常監視backendで、samplingやcontent capture policyを分けられます。

注意点

自動instrumentationだけでは、agentがなぜそのtoolを選んだか、どのbusiness ruleを通過したかまでは見えないことがあります。QAに必要なsemantic spanは自前で追加する前提を持つべきです。

対応frameworkが多いほど、各instrumentationのspan粒度や安定性に差が出ます。CIの評価器は、実際に出るtrace schemaをsampleで固定してから作るのが安全です。
