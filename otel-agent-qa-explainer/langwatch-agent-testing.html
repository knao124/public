LangWatch Agent Simulationsは、unit test、component eval、agent simulationの三層でagentを評価し、multi-turn scenarioで会話、tool call、状態遷移を検査する方法を説明します。

読む前の地図

toolやretrievalをtraceできるようになった後に読む資料です。agent QAを単発input-outputから、会話全体の振る舞いへ広げる発想が得られます。

短い根拠引用

Agents aren’t simple input-output functions

agentを単発関数ではなくprocessとして評価する必要性を示す短い表現。

資料の流れを復元する

資料は、従来のevalが単純なinput-output関数を前提にしていることを問題視します。agentは会話し、状態を持ち、toolを呼び、途中で判断を変えるprocessです。したがって最終回答だけを見ても、どこで失敗したかは分かりません。

次に、評価を三層に分けます。Level 1は通常コードやtoolのunit/integration testです。toolが単体で正しく動くかを検査します。Level 2はRAGやLLM callなど部品のevalです。retrieval relevanceや回答品質を部品単位で見ます。Level 3がagent simulationです。

agent simulationでは、ユーザー役が複数turnで会話し、agentが適切に質問し、toolを呼び、ticketを作り、必要ならhuman handoffします。期待値は最終回答だけではなく、中間のtool call、label、state transitionにも置かれます。

資料は、scenarioが実務の失敗を再現する単位になることを示します。productionで起きた失敗会話を短くscenario化し、以後のprompt/model/tool変更で再発しないか確認します。

何が学べるか

最大の学びは、agent QAではユーザーもテスト対象の一部になることです。ユーザーが曖昧に言う、怒っている、途中で条件を変える、必要情報を出し渋る、という状況でagentが正しく振る舞えるかを見ます。

また、scenarioには中間期待を書くべきだと分かります。返金ポリシーを確認する、注文IDを確認する、該当toolを呼ぶ、human escalation条件を満たしたらhandoffする、といった期待です。

この考え方により、LLM-as-Judgeの曖昧な総合点だけでなく、業務上重要な状態遷移を検査できます。

Agent自動QAへ落とす手順

まず上位10件の業務フローをscenario化します。返金、配送遅延、予約変更、障害対応、申請承認など、途中にtoolと状態遷移があるものを優先します。

次に、各scenarioに中間expectationを置きます。例として、policy search toolが呼ばれる、customer lookupが1回だけ呼ばれる、write APIは承認前に呼ばれない、ticket labelが正しい、などです。

さらに、本番失敗からscenarioを増やします。ユーザー低評価traceやincident traceを読み、最小再現scenarioへ落とします。これをCIまたはnightlyで回すことで、prompt変更による回帰を検出できます。

注意点

user simulatorを完全にLLM任せにすると、現実離れした会話になることがあります。seed scenarioは人間が書き、言い換えや難易度調整だけLLMに任せる方が安定します。

simulationは網羅ではありません。本番traceのsampling、annotation、error analysisと併用し、現実の失敗からscenarioを増やす運用が必要です。

scenarioをどう書けば品質保証になるか

LangWatchのsimulationを使うとき、scenarioは単なる会話例ではなく品質保証の契約になります。ユーザーの発話、agentの応答、期待tool call、期待状態、禁止行動を明示します。これにより、agentの自由度を残しながら、業務上外せない行動だけを固定できます。

multi-turn scenarioでは、最終回答より中間expectationが重要です。返金相談なら、ポリシー検索、注文確認、条件判定、必要ならhandoff、という順序があります。最終回答が丁寧でも、承認前に返金処理toolを呼んだら失敗です。

production failureからscenarioを作ると、simulationは回帰テストになります。実際に起きた失敗会話を短くし、再現に必要なturnだけ残し、expected tool/stateを追加します。

実装チェックポイント

  • scenarioにユーザーの曖昧さや変更を含める
  • 最終回答だけでなく中間tool callを期待値にする
  • 禁止行動を明示する
  • 本番失敗traceからscenarioを増やす
  • user simulatorの出力を人間がレビューする
