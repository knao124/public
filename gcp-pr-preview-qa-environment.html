GCPで作るブランチ環境

目的: AI Agentがタスクごとにbranchを切り、localではなく専用環境で常に動作確認できるようにする。

この資料では、その専用環境を ブランチ環境 と呼ぶ。 初期構成は Cloud Run service per branch + Cloud SQL branch-env instance + branchごとのdatabase/user を推奨する。 GCPだけで始める場合、DB branching相当をCloud SQLのdatabase/user分離で代替するのが、コストと運用負荷のバランスが良い。

読む前に

この資料は、Webアプリのbranchごとに専用の確認環境を自動で作り、AI Agentに動作確認させるためのGCP初期構成を説明する。 PRはbranchをレビューに出す段階であり、環境作成の起点ではなくレビューとmerge判断の単位である。 Agentはタスクを割り当てられたらbranchを切り、ブランチ環境を立ち上げ、localではなくその環境で常に確認する。

設計原則

共有stagingは、並列branchとAI Agent QAの前提に合わない。状態が汚れ、誰の変更が原因か追いにくく、Agentが破壊的操作をできない。 QA環境は「守る場所」ではなく「壊してよい使い捨て環境」として設計する。

原則 1 branch = 1 URL

branchごとにCloud RunのURLを発行し、AgentはそのURLだけを操作する。

原則 1 branch = 1 DB

Cloud SQL内にbranch専用database/userを作り、他branchや本番へ影響させない。

原則 local確認を前提にしない

Agentの動作確認はブランチ環境で行う。localは補助であり、判定根拠にはしない。

推奨初期構成

要点は、branchが作られたら「動くアプリ」と「専用データ」を作り、Agentが触り、branchが終わったら消すこと。 下の流れはGCPサービス名の羅列ではなく、責任の境界ごとに分けた最小単位である。 

Agent task
  -> Git branch 作成
  -> GitHub Actions
  -> Artifact Registry に image push
  -> Cloud Run に br-task-123-web service deploy
  -> Cloud SQL branch-env instance に br_task_123 database/user 作成
  -> migration + seed
  -> Agent QA / Playwright
  -> 結果をcommit statusまたはPRコメントへ記録
  -> branch削除またはPR closeでCloud Run service / DB / user / secret / imageを削除
単位 なぜ分けるか 消すタイミング
GitHub Actions workflow branch作成、branch更新、PR close、branch削除をきっかけに同じ手順を再現するため。 消さない。repo側の自動処理として残す。
Artifact Registryのimage そのbranchのcommitでbuildした実行物を固定するため。deployとQAが同じimageを見る。 TTLまたはcleanup policyで削除。
Cloud Run service branchごとにURLとruntimeを分けるため。Agentが自由に操作しても他branchへ影響しない。 branch削除 / PR close / merge、またはTTL超過。
Cloud SQL database/user branchごとにデータを分けるため。migrationや入力データの破壊をそのbranch内に閉じる。 branch削除 / PR close / merge、またはTTL超過。
Secret Managerのbranch用secret branch専用DB URLや環境アクセス用authをCloud Runに渡すため。本番secretと混ぜない。 対応するCloud Run serviceと同時に削除。
QA artifact Agentの判定根拠を人間が後から確認するため。 数日から数週間保持し、Storage lifecycleで削除。

この粒度にする理由は、作成・更新・削除の責任を明確にするため。 「branchごとに変わるもの」はworkflowで短命リソースとして作り、「常に必要な土台」はTerraformなどで恒久リソースとして管理する。

GCPサービスの役割

サービス 担当するもの この構成で作るもの 運用上の注意
Cloud Run branchごとのWeb/API実行環境 br-task-123-web のようなservice。min instances=0、max instances=1-2。 Agent用には公開URL + アプリ側のブランチ環境authが扱いやすい。
Cloud SQL for PostgreSQL branchごとのDB分離 1つのbranch-env-postgres instanceにbranchごとのdatabase/userを作成。 NeonのようなDB branchではない。厳密な物理隔離が必要なら後で再検討する。

Secret Manager branch専用secretの受け渡し DB URL、basic auth password、test API keyをbranch単位で作成。 production secretはbranch-env projectへ持ち込まない。
Cloud Storage QA artifact保存 gs://myapp-branch-env-artifacts/br-task-123/ にtraceやvideoを保存。 lifecycle ruleで一定期間後に削除する。
Cloud Scheduler reaper起動 毎日または数時間ごとに古いブランチ環境を削除。 branch削除やPR close webhook漏れの保険として必須。

DB分離方針

Neonの公式docsでは、database branchをcopy-on-writeの独立したbranchとして作り、開発・テスト・preview用途に使えると説明されている。 参考: Neon Branching docs / Neon Database Branching Workflows。 一方、GCPのCloud SQLにはこれと同等の軽量なDB branching機能はない。 そのため、GCPだけで始める初期案では、1つのbranch-env用Cloud SQL instanceにbranchごとのdatabaseとuserを作る。 

Cloud SQL instance: branch-env-postgres

databases:
  br_task_101
  br_task_102
  br_task_103

users:
  br_task_101_user -> br_task_101 のみ接続
  br_task_102_user -> br_task_102 のみ接続
  br_task_103_user -> br_task_103 のみ接続

この方式は「論理分離」であり、Cloud SQL instance自体は共有する。初期コストを抑えるには妥当だが、 負荷試験、権限分離の強化、拡張機能の衝突、DBバージョン差分検証が必要になったら、 instance per branchや外部DB branchingの併用を検討する。

Agent QAの動かし方

Agentにはブランチ環境URL、test user、確認観点、branch diffだけを渡す。production credentialや共有staging credentialは渡さない。 結果はcommit statusに残し、PRがある場合はPRコメントにも残す。 

Branch environment: https://br-task-123-web-xxxxx.a.run.app
Branch: agent/task-123
Commit: abc123
Database: br_task_123

Result: failed

Findings:
- /checkout で500
- 390px幅でCTAが操作不能
- console error: TypeError at CartSummary.tsx:42

Artifacts:
- screenshot
- Playwright trace
- video
- network log

merge判定は「Agentが触った」ではなく、再現可能なartifactとfail/passの根拠で行う。 Playwright trace、console log、screenshot、network errorを残すと、失敗時の再調査が短くなる。

セキュリティとコスト制御

領域 ルール 理由 最小実装
Secret 本番secretを渡さない Agentは破壊的操作をする前提なので、漏洩や誤送信の事故範囲を本番ではなくbranch-env project内に閉じる。 Secret Managerにtest用secretだけを作り、Cloud Runへbranch単位でmountする。
Access ブランチ環境authを入れる Cloud Run URLは外から到達できるため、検索流入や第三者アクセスを避ける必要がある。 初期はアプリ側basic authまたは短命token。厳格化時にIAPやCloud Run IAMを検討する。
External API 外部送信をsandboxへ逃がす メール、SMS、決済、Webhookを本物に送ると、Agent QAが顧客影響を起こす。 決済はtest mode、メールはsink、Webhookはmock endpointを使う。
Cost scale-to-zeroを前提にする branchは並列に増えるため、使っていない環境の常時起動費を持たない。 Cloud Runはmin instances=0、max instances=1-2にする。
Cleanup TTL reaperを必須にする branch削除やPR close webhookだけに依存すると、消し忘れが必ず発生する。 resource labelにbranch名とexpires_atを付け、Cloud Schedulerから定期削除する。
Data seedを軽くする 本番dumpは漏洩リスクと復元時間が大きい。Agent QAに必要なデータだけでよい。 匿名fixtureと最小seedを用意し、branch DB作成後に投入する。
Limit 上限を明示する Agentが大量にbranchを作ると、意図せずCI時間、DB容量、artifact容量が増える。 同時ブランチ環境数、Agent QA時間、artifact保持期間、DBサイズに上限を入れる。

実装ステップ

1. 名前と境界を決める

  1. 環境名を「ブランチ環境」に統一する。
  2. branch名から環境IDを作るルールを決める。
  3. 環境IDに使えない文字を置換するルールを決める。
  4. Cloud Run service名の形式を決める。
  5. Cloud SQL database名の形式を決める。
  6. Secret Manager secret名の形式を決める。
  7. artifact保存先prefixの形式を決める。

2. 恒久リソースを用意する

  1. ブランチ環境専用のGCP projectを作る。
  2. Artifact Registry APIを有効化する。
  3. Cloud Run APIを有効化する。
  4. Cloud SQL Admin APIを有効化する。
  5. Secret Manager APIを有効化する。
  6. Cloud Storage APIを有効化する。
  7. Cloud Scheduler APIを有効化する。
  8. Artifact Registry repositoryを作る。
  9. branch-env用Cloud SQL instanceを作る。
  10. QA artifact用Cloud Storage bucketを作る。
  11. reaper用Cloud Run jobまたはCloud Run serviceを作る。
  12. ここまでの恒久リソースをTerraformで管理する。

3. GitHub ActionsからGCPへ認証する

  1. GitHub OIDC用のWorkload Identity Poolを作る。
  2. GitHub repository用のWorkload Identity Providerを作る。
  3. deploy用service accountを作る。
  4. deploy用service accountにArtifact Registry push権限を付ける。
  5. deploy用service accountにCloud Run deploy権限を付ける。
  6. deploy用service accountにCloud SQL管理権限を付ける。
  7. deploy用service accountにSecret Manager管理権限を付ける。
  8. GitHub ActionsでGCPへkeyless認証できることを確認する。

4. deploy workflowを作る

  1. branch pushでworkflowを起動する。
  2. branch名から環境IDを計算する。
  3. container imageをbuildする。
  4. container imageをArtifact Registryへpushする。
  5. branch専用databaseを作る。
  6. branch専用DB userを作る。
  7. branch専用DB URLをSecret Managerに保存する。
  8. migrationを実行する。
  9. seedを投入する。
  10. Cloud Run serviceを作成または更新する。
  11. Cloud Run serviceへbranch名とexpires_atのlabelを付ける。
  12. ブランチ環境URLをcommit statusまたはPRコメントに記録する。

5. QA workflowを作る

  1. Cloud Run serviceのhealth checkを待つ。
  2. QA用test userを作る。
  3. Playwrightの基本導線テストを実行する。
  4. AI Agentにbranch diffと確認観点を渡す。
  5. AI Agentにブランチ環境URLだけを操作させる。
  6. console errorを収集する。
  7. network errorを収集する。
  8. screenshotを保存する。
  9. Playwright traceを保存する。
  10. QA結果をcommit statusまたはPRコメントに記録する。

6. cleanup workflowを作る

  1. branch削除でcleanup workflowを起動する。
  2. PR closeでcleanup workflowを起動する。
  3. 対象のCloud Run serviceを削除する。
  4. 対象のCloud SQL databaseを削除する。
  5. 対象のCloud SQL userを削除する。
  6. 対象のSecret Manager secretを削除する。
  7. 対象のartifact prefixを削除対象にする。
  8. 対象のcontainer imageをcleanup policyの対象にする。
  9. Cloud Schedulerでreaperを定期実行する。
  10. reaperでTTL超過のブランチ環境を削除する。

拡張判断: 何が起きたら何を強くするか

初期構成は低コストで始めるためのもの。問題の兆候、困る理由、次の打ち手をセットで判断する。

兆候 困ること 次の打ち手
DB負荷がbranch間で干渉する 1つのCloud SQL instanceを共有しているため、重いQAやmigrationが他branchの確認を遅くする。 Cloud SQL instance per branchにする。もしくはNeonなどのDB branchingを併用する。
DBを完全に分離したい database/user分離では、instance設定、拡張機能、DBバージョン、性能上限は共有されたままになる。 instance per branch、またはcopy-on-write型の外部DB branchingを検討する。
複数service構成になった Web、API、worker、batchを個別にdeployすると、branch環境の作成手順が散らばる。 environment manifestを作り、service一覧からCloud Run service群を生成する。
Agent QAが長くなった GitHub Actionsのqueue、課金、timeoutがボトルネックになる。 QAを分割する。cacheを入れる。必要ならself-hosted runnerを使う。
外部API連携が増えた sandboxのないAPIやWebhookが増えると、Agent QAが外部へ副作用を出しやすい。 mock server、contract test、sandbox proxyを整備する。
アクセス制御を強くしたい basic authや短命tokenでは、監査、個人別権限、組織外共有の制御が弱い。 IAP、Cloud Run IAM、または社内SSO連携の環境アクセスgatewayを検討する。
