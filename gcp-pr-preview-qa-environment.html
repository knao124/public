GCPで作るPR専用Preview/QA環境

目的: AI AgentがPRごとの専用環境を自由に操作し、共有stagingを待たずに動作確認できるようにする。

初期構成は Cloud Run service per PR + Cloud SQL preview instance + PRごとのdatabase/user を推奨する。 GCPだけで始める場合、DB branching相当をCloud SQLのdatabase/user分離で代替するのが、コストと運用負荷のバランスが良い。

読む前に

この資料は、WebアプリのPRを出すたびに専用の確認環境を自動で作り、AI Agentに動作確認させるためのGCP初期構成を説明する。 先に登場人物と章立てを押さえると、後続のサービス名や処理順が読みやすい。

設計原則

共有stagingは、並列PRとAI Agent QAの前提に合わない。状態が汚れ、誰の変更が原因か追いにくく、Agentが破壊的操作をできない。 QA環境は「守る場所」ではなく「壊してよい使い捨て環境」として設計する。

原則 1 PR = 1 URL

PRごとにCloud RunのURLを発行し、AgentはそのURLだけを操作する。

原則 1 PR = 1 DB

Cloud SQL内にPR専用database/userを作り、他PRや本番へ影響させない。

原則 自動削除

PR close、merge、TTL超過でruntime、DB、secret、artifactを削除する。

推奨初期構成

要点は、PRが開いたら「動くアプリ」と「専用データ」を作り、Agentが触り、PRが終わったら消すこと。 下の流れはGCPサービス名の羅列ではなく、責任の境界ごとに分けた最小単位である。 

GitHub PR
  -> GitHub Actions
  -> Artifact Registry に image push
  -> Cloud Run に pr-123-web service deploy
  -> Cloud SQL preview instance に pr_123 database/user 作成
  -> migration + seed
  -> Agent QA / Playwright
  -> 結果をPRコメント
  -> PR closeでCloud Run service / DB / user / secret / imageを削除
単位 なぜ分けるか 消すタイミング
GitHub Actions workflow PR作成、PR更新、PR closeをきっかけに同じ手順を再現するため。 消さない。repo側の自動処理として残す。
Artifact Registryのimage そのPRのcommitでbuildした実行物を固定するため。deployとQAが同じimageを見る。 TTLまたはcleanup policyで削除。
Cloud Run service PRごとにURLとruntimeを分けるため。Agentが自由に操作しても他PRへ影響しない。 PR close / merge、またはTTL超過。
Cloud SQL database/user PRごとにデータを分けるため。migrationや入力データの破壊をそのPR内に閉じる。 PR close / merge、またはTTL超過。
Secret ManagerのPR用secret PR専用DB URLやpreview authをCloud Runに渡すため。本番secretと混ぜない。 対応するCloud Run serviceと同時に削除。
QA artifact Agentの判定根拠を人間が後から確認するため。 数日から数週間保持し、Storage lifecycleで削除。

この粒度にする理由は、作成・更新・削除の責任を明確にするため。 「PRごとに変わるもの」はworkflowで短命リソースとして作り、「常に必要な土台」はTerraformなどで恒久リソースとして管理する。

GCPサービスの役割

サービス 役割 初期設定 注意点
Cloud Run PRごとのWeb/API実行環境 min instances=0、max instances=1-2、service名はpr-123-web Agent用に公開URL + アプリ側preview authが扱いやすい。
Cloud SQL for PostgreSQL preview用DB基盤 1つのpreview-postgres instanceにPRごとのdatabase/userを作成 NeonのようなDB branchではない。厳密な物理隔離が必要なら後で再検討する。
Artifact Registry PRごとのcontainer image保存 web:pr-123-sha のようにtag付け cleanup policyで古いpr-* imageを削除する。
Secret Manager PR専用secretの受け渡し DB URL、basic auth password、test API keyをPR単位で作成 production secretはpreview projectへ持ち込まない。
Cloud Storage QA artifact保存 gs://myapp-preview-artifacts/pr-123/ にtraceやvideoを保存 lifecycle ruleで一定期間後に削除する。
Cloud Scheduler reaper起動 毎日または数時間ごとに古いpreviewを削除 PR close webhook漏れの保険として必須。

PRライフサイクル

1 PR作成

GitHub ActionsがPR番号とcommit SHAを取得する。

2 Build

container imageをbuildし、Artifact Registryへpushする。

3 DB準備

pr_123 database/userを作成し、migrationとseedを実行する。

4 Deploy

Cloud Run service pr-123-web を作成または更新する。

5 Agent QA

preview URLをPlaywrightやAI Agentが操作し、結果をartifact化する。

6 Cleanup

PR close、merge、TTL超過で短命リソースを削除する。

DB分離方針

GCPだけで構成する場合、Neonのような「branch per PR」はCloud SQLにはない。 そのため、初期は1つのpreview用Cloud SQL instanceにPRごとのdatabaseとuserを作る。 

Cloud SQL instance: preview-postgres

databases:
  pr_101
  pr_102
  pr_103

users:
  pr_101_user -> pr_101 のみ接続
  pr_102_user -> pr_102 のみ接続
  pr_103_user -> pr_103 のみ接続

この方式は「論理分離」であり、Cloud SQL instance自体は共有する。初期コストを抑えるには妥当だが、 負荷試験、権限分離の強化、拡張機能の衝突、DBバージョン差分検証が必要になったら、 instance per PRや外部DB branchingの併用を検討する。

Agent QAの動かし方

Agentにはpreview URL、test user、確認観点、PR diffだけを渡す。production credentialや共有staging credentialは渡さない。 結果は人間が追える形でPRに残す。 

Preview: https://pr-123-web-xxxxx.a.run.app
Commit: abc123
Database: pr_123

Result: failed

Findings:
- /checkout で500
- 390px幅でCTAが操作不能
- console error: TypeError at CartSummary.tsx:42

Artifacts:
- screenshot
- Playwright trace
- video
- network log

merge判定は「Agentが触った」ではなく、再現可能なartifactとfail/passの根拠で行う。 Playwright trace、console log、screenshot、network errorを残すと、失敗時の再調査が短くなる。

セキュリティとコスト制御

Security 本番secretを渡さない

preview projectにはtest用secretだけを置く。外部APIはsandbox、mock、sinkを使う。

Security preview authを入れる

Cloud Run IAMより、初期はアプリ側basic auth/tokenの方がAgent QAと相性がよい。

Cost scale-to-zero前提

Cloud Runはmin instances=0。PR環境の最大instance数も小さく固定する。

Cost TTL reaper必須

PR close webhookだけに依存しない。古いservice、DB、secret、imageを定期削除する。

Data seedを軽くする

本番dumpではなく、確認に必要な匿名fixtureだけを投入する。

Ops 上限を決める

同時preview数、Agent QA時間、max instances、artifact保持期間に上限を入れる。

実装ステップ

  1. preview専用GCP projectを作り、Artifact Registry、Cloud Run、Cloud SQL、Secret Manager、Cloud Storageを有効化する。
  2. GitHub ActionsからGCPへWorkload Identity Federationでdeployできるようにする。
  3. 恒久リソースをTerraformで作る。短命なPRリソースはworkflow scriptで作る。
  4. deploy-preview workflowを作り、image build、DB作成、migration、Cloud Run deploy、PRコメントまで実装する。
  5. qa-preview workflowを作り、Playwright/Agent QAとartifact保存を実装する。
  6. cleanup-preview workflowとscheduled reaperを作り、PR close漏れや古い環境を削除する。

いつ構成を強くするか

初期構成は低コストで始めるためのもの。次の兆候が出たら構成を強化する。

  • Cloud SQL preview instanceの負荷がPR間で干渉する。
  • DB拡張、migration、権限、バージョン差分をPRごとに完全分離したい。
  • 複数service構成になり、service per PRの作成数が増える。
  • Agent QAの実行時間が長くなり、GitHub Actions costやqueueが問題になる。
  • 外部API連携が多くなり、sandboxやmockの整備が必要になる。

その段階で、Cloud SQL instance per PR、外部DB branching、preview専用のself-hosted runner、 Cloud Deployやより厳密なpolicy enforcementを検討する。最初から全部入れる必要はない。
