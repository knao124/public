「ループでプロンプトがいらなくなる」は、何が変わる話か

Claude Code / Boris Cherny インタビューの読み解き

結論から言うと、「プロンプトが不要になる」は、人間の意図が不要になるという意味ではありません。 人間が毎回その場で命令文を書く代わりに、あらかじめ作ったループが状況を見て、Claudeに渡す次の指示を生成し続ける、という意味です。

まず、この動画は何を言っているか

この動画は、AnthropicのBoris Chernyが、Claude Codeの誕生、社内での使われ方、Claude Coworkへ広がった理由、 そして「人間が毎回プロンプトを書く」段階から「ループがClaudeに次の仕事を渡す」段階へ移る見通しを話すインタビューです。 ただの製品紹介ではなく、AIで組織・職能・プロダクト開発の単位がどう変わるかを、具体例を使って説明しています。

前提: ここでのループは単なる while 文ではない

ここでの「ループ」は、コード上の反復処理だけを指していません。実務上は、目的・入力・判定基準・実行手段を持った小さなワークフローです。 たとえば「GitHub issueを読む、候補タスクを選ぶ、Claudeに実装方針を作らせる、結果を確認する、ダメなら次の修正指示を出す」までを回す単位です。

つまり、プロンプトを書く場所が「チャット欄」から「ループの設計」に移ります。

3段階で見るとわかりやすい

1. 人がコードを書く

IDEで人間が主にコードを書く。AIは補完や相談役。AIへの指示は補助的です。

2. 人がClaudeに都度指示する

人間が「この関数を直して」「テストを追加して」と毎回プロンプトを書く。複数のClaudeセッションを並列に動かすこともあります。

3. ループがClaudeに次の指示を出す

人間が毎回プロンプトを書くのではなく、ループが状況を読み、次にClaudeへ渡す仕事を作ります。

人間の仕事は消えない

人間は「何を回すか」「成功条件は何か」「止める条件は何か」を設計します。Borisの言う仕事はここです。

ループの中身

典型的には、次の4つが回ります。

1. 観察 Issue、PR、Slack、ログ、テスト結果、ユーザーフィードバックなどを見る。
2. 判断 何をClaudeに任せるか、どの情報を渡すか、どの順で処理するかを決める。
3. 指示生成 Claudeに渡すプロンプト、制約、期待出力、検証方法を組み立てる。
4. 確認 結果をテスト・レビュー・差分・メトリクスで見て、次の周回へ進むか止める。

具体例: 「バグを直して」と毎回言わない

人が都度プロンプトを書く場合はこうなります。

このissueを読んで原因を推測して。
次に該当ファイルを探して。
修正案を出して。
テストを書いて。
失敗したのでログを見て直して。

ループ化すると、人は次のような設計をします。

目的: 未解決issueから小さなバグ修正候補を見つける
入力: GitHub issue、直近ログ、関連テスト、既存コード
Claudeへの依頼: 原因仮説、修正案、テスト案、差分レビュー
検証: テストが通る、差分が小さい、仕様逸脱がない
停止条件: 2回失敗、影響範囲が大きい、権限が必要、人間レビューが必要

この状態になると、人間は毎回「次はログを見て」「次はテストして」と書かなくてもよくなります。 ループが失敗結果を見て、次のClaudeへの依頼を作るからです。

なぜ「プロンプトがいらない」ように見えるのか

  • 人間が書く単発プロンプトは減る。代わりに、ループが毎回の依頼文を作る。
  • 人間は作業単位ではなく、仕組み単位で指示する。「このPRを直して」ではなく「この種類のPR修正を回す」です。
  • 複数セッションを同時に動かせる。各Claudeは個別のタスクを処理し、ループが結果を集めます。
  • 価値が出るのは、Claudeの能力だけでなく、観察・制約・検証・停止条件をどう組むかです。

ただし、魔法ではない

ループ化しても、人間の判断が完全に消えるわけではありません。むしろ設計責任は上流に移ります。

  • 悪いループは、悪いプロンプトを高速に大量生産します。
  • 成功条件が曖昧だと、Claudeは「それっぽい進捗」を作りやすいです。
  • 止める条件がないと、誤った方向に自動で進み続けます。
  • 権限、セキュリティ、顧客影響がある作業は、人間レビューをループに組み込む必要があります。

実務で試すなら、小さいループから

  1. まず「繰り返し発生するが、失敗しても被害が小さい作業」を選ぶ。
  2. Claudeに渡す材料を固定する。例: issue本文、関連ファイル、テストログ。
  3. 期待出力を固定する。例: 原因仮説、修正案、検証コマンド、リスク。
  4. 検証と停止条件を先に決める。例: テスト失敗2回で停止、人間レビュー必須。
  5. 結果を見て、プロンプトではなくループ設計を直す。
